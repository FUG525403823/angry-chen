# O05 快照编码增量化与自适应快照率

> 里程碑：O5 ｜ 预估：1 会话 ｜ 上游移交物：HANDOFF-O04

## 0. 现状与不足（证据）

本步处理**快照通道**：编码/解码里各有一段 1024 槽的全量扫描，截断路径有两次全排序，而"自适应快照率"这个
已经冻结进协议的字段（`snapshotRateX10`）从头到尾是个常量。

### 0.1 结论一：编码与解码各有一次 1024 槽全量扫描

| 事实 | 证据 |
|---|---|
| `encodeSnapshot` 的删除列表遍历 `for (let id = 1; id <= MAX_ENTITIES; id += 1)`，逐 id 查两个 `Uint8Array` | `packages/shared/src/net/codec.ts:600-614` |
| `MAX_ENTITIES = 1024` | `packages/shared/src/config/entity.ts:2` |
| `decodeSnapshot` 在基线全量帧与每帧末尾各重建一次 `mirror.ids`（同样是 1024 全扫 + `push`） | `packages/shared/src/net/codec.ts:640-646,660-666` |
| `mirror.ids` 是普通 `number[]`（`push` 会增长/搬迁） | `packages/shared/src/net/codec.ts:445-456` |
| 规模 | 4 会话 × 20Hz = 每秒 8.2 万次纯空转迭代（无实体死亡时全部浪费） |

### 0.2 结论二：快照截断路径两次全排序 + 一个对象分配

| 事实 | 证据 |
|---|---|
| `truncated` 时先 `collectNearest`（全量 `push` + 按距离 `sort` + 按 id 再 `sort`） | `packages/shared/src/snapshot.ts:100-116` |
| `playersCentroid` 每次返回 `{x, z}` 对象字面量 | `packages/shared/src/snapshot.ts:81-98` |
| 复用同一个 `world.scratchEntities`（共享可变数组） | `packages/shared/src/snapshot.ts:100-112` |
| 触发条件 | 活动实体数 > `NET.snapshotMaxEntities = 256`；满编 60 羊时不会触发，但 10 波后的召唤潮会 |

### 0.3 结论三：`snapshotRateX10` 是死配置

| 事实 | 证据 |
|---|---|
| 常量 `SNAPSHOT_RATE_X10 = 200` | `packages/shared/src/net/protocol.ts:135,154-158` |
| 房间初始化即固定 200，全生命周期不变 | `packages/server/src/room.ts:90,130,248` |
| 只经 pong 下发（`encodePong` 第 9 字节） | `packages/shared/src/net/codec.ts:390-397` |
| 客户端只存不用于插值 | `packages/client/src/net/connection.ts:170,281,359` |
| 快照无条件每 tick 发送（仅"每 40 tick 一次全量"这一条策略） | `packages/server/src/room.ts:483-500,513-530`、`packages/shared/src/net/protocol.ts:127` |

### 0.4 结论四：客户端插值延迟是固定 100ms

| 事实 | 证据 |
|---|---|
| `INTERPOLATION_DELAY_MS = 100`，与快照率、RTT、抖动全无关系 | `packages/client/src/net/state.ts:16` |
| 插值窗口 `SNAPSHOT_HISTORY = 6` 个关键帧 | `packages/client/src/net/state.ts:17,107` |
| 服务器时间外推：`latestServerTimeMs + (now() - latestRecvAtMs)` | `packages/client/src/net/state.ts:257` |
| 影响 | 丢包/抖动时 100ms 缓冲不足（证据里 `snapshotArrivalJitterP95Ms = 20–27ms`），而 20Hz 下 100ms 又偏大（相当于 2 帧） |

### 0.5 结论五：带宽现状（说明优化目标不是"省字节"）

证据文件记录快照均值 88.2B、最大 482B、每客户端带宽 1.81KB/s，门槛是 1200B / 40KB/s——
所以本步的目标是**CPU 与自适应能力**，不是压缩字节；协议字节格式必须保持不变。

## 1. 目标

本步骤结束后：

1. 编码删除列表与解码 `mirror.ids` 的维护量从 O(1024) 降到 O(本帧增删数)，**线上字节格式完全不变**；
2. 截断路径从"两次全排序"降到"一次部分选择 + 对小结果集排序"；
3. `snapshotRateX10` 从常量变成**受控的离散档位**（默认仍 20Hz，只在拥塞时降档），并真正用于客户端插值延迟；
4. 客户端插值延迟动态化，取值有界、可解释。

判据：`node tools/bots.mjs --players 4 --minutes 5 --strict` 的 S5.2-1/2/3（字节均值、带宽、19–21/s 速率）与其余门槛全部 PASS，
且 `snapshot-codec.test.ts` 的既有字节断言（不修改）全部通过。

## 4. 任务清单

- [ ] 1. `codec.ts`：`SnapshotBaseline` 增加 `readonly presentIds: Uint16Array` 与 `presentCount: number`（升序紧凑列表）。`encodeSnapshot` 写入新实体时在列表尾部插入并保持升序；删除列表改为遍历 `presentIds[0..presentCount)`；输出顺序保持**升序**（与旧实现逐字节一致）。
- [ ] 2. `codec.ts`：`SnapshotMirror.ids` 改为 `Uint16Array` + `idCount`；解码时对"新增 id"插入升序、对"删除 id"做有序移除；`baselineTick === 0` 时清空。删除每帧末尾的 1024 全扫。
- [ ] 3. `codec.ts`：新增两个内部断言函数（仅测试用导出）：`baselinePresentIdsSorted(baseline)`、`mirrorIdsSorted(mirror)`，供测试断言不变量。
- [ ] 4. `snapshot.ts`：`collectNearest` 改为"有界最大堆部分选择"（容量 = `capacity`），选出后再按 id 升序排一次（只排 N 个）；`playersCentroid` 写入模块级 `centroidScratch`。
- [ ] 5. `room.ts`：`snapshotRateX10` 离散档位 `{200, 150, 100}`；发送节拍用 tick 取模实现（200 → 每 tick；150 → 每 3 tick 发 2 次；100 → 每 2 tick 发 1 次），`sendSnapshot` 与事件帧解耦（事件帧仍每 tick 发送）。

## 5. 冻结契约

```ts
// packages/shared/src/net/codec.ts
export interface SnapshotBaseline {
  // …既有 present/nextPresent/bytes/tick…
  readonly presentIds: Uint16Array;   // 上一 tick 已发布实体 id，升序紧凑
  presentCount: number;
}
export interface SnapshotMirror {
  // …既有字段…
  readonly ids: Uint16Array;   // 当前存在实体 id，升序紧凑（原为 number[]）
  idCount: number;
}

// packages/shared/src/net/protocol.ts → LIMITS 新增
snapshotRateLevels: readonly number[];   // [200, 150, 100]，单位 1/10 Hz
snapshotRateDownshiftMs: 3000;           // 无拥塞持续多久升一档
```

| 冻结项 | 值 / 定义 |
|---|---|
| 线上字节格式 | **完全不变**（删除列表升序、记录 15 字节、帧头不变）；本步不得改协议 |
| 速率档位 | 200 = 每 tick；150 = 每 3 tick 发 2 次；100 = 每 2 tick 发 1 次（离散，白盒可断言） |
| 降档触发 | 最慢会话 `bufferedAmount > maxBufferedBytes / 2` 或 `tickSkips` 增长或 `ac_room_budget_exceeded_total` 增长 |
| 升档触发 | 连续 `3000ms` 无触发条件，升一档，上限 200 |
| 插值延迟 | `clamp(2 × medianSnapshotIntervalMs, 100, 250)`；样本不足 60 时用 `snapshotRateX10` 推算 |
| 全量帧节拍 | 保持 `LIMITS.fullSnapshotIntervalTicks = 40`（降档时仍按 tick 计数判定） |
| 事件帧 | 不受速率档位影响，仍每 tick 广播（`room.ts` 的事件帧路径与 `sendSnapshot` 解耦） |

## 8. 风险与回滚

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 紧凑列表顺序不稳导致快照字节不可复现 | `snapshot.test.ts` 逐字节断言失败 | 删除列表强制升序输出；`presentIds` 维护时保持升序；测试断言"升序且无重复" |
| `mirror.ids` 类型从 `number[]` 改为 `Uint16Array` 破坏客户端消费点 | `state.ts` 的类型检查或运行时报错 | `idCount` 取代 `.length`；先在 `shared` 内部完成替换并跑 `pnpm typecheck`，再改客户端 |
| 降档让玩家感到卡顿 | 压测中 `snapshotArrivalJitterP95Ms` 上升或掉帧 | 默认不下调；只有在实测拥塞指标触发时才降，且最低 10Hz；降档事件计数可在 O10 加告警 |
| 插值延迟过大导致手感"糊" | 实测 p95 延迟 > 250ms 或位置滞后明显 | 上限硬钳 250ms；间隔中位数用 60 样本窗口，避免抖动导致频繁改变 |
| 部分选择算法在"全部实体等距"时与旧行为不同 | `snapshot.test.ts` 失败 | 平局统一按 id 升序决胜（与旧实现的两段排序等价），写进 §5 |
| 回滚目标 | — | 回滚 = `git revert` 本次提交（codec/snapshot/room/metrics/client state+connection + 测试 + 证据），回到 HANDOFF-O04 状态；协议未变，无需客户端兼容处理 |
