# O03 出站帧所有权与背压

> 里程碑：O3 ｜ 预估：1 会话 ｜ 上游移交物：HANDOFF-O02

## 0. 现状与不足（证据）

本步处理的是**数据完整性 + 内存稳健性**问题：服务器把所有出站帧都写进复用缓冲，
而 `ws` 在服务端方向（不掩码）**不拷贝 payload**，于是"写进 socket 之后又改写同一块内存"会直接损坏线上帧。

### 0.1 结论一：服务端发出的每一条帧都是"零拷贝引用"，而发送方复用了缓冲区

| 事实 | 证据 |
|---|---|
| `Connection.send` 直接把调用方的数组交给 `ws` | `packages/server/src/transport/ws-adapter.ts:44-54` |
| `ws` 的 `toBuffer` 对任何 `ArrayBufferView` 是 `new FastBuffer(data.buffer, data.byteOffset, data.byteLength)`——**共享同一块内存** | `node_modules/.pnpm/ws@8.21.3/node_modules/ws/lib/buffer-util.js:87-104` |
| `ws` 的 `Sender.frame()` 在不掩码（服务端）时 `if (!options.mask) return [target, data];`——`target` 只是帧头，payload 就是调用方的视图 | `node_modules/.pnpm/ws@8.21.3/node_modules/ws/lib/sender.js:96-160`（尤其 `:142` 与 `:155`） |
| `Sender.sendFrame` 对两段式列表**直接** `socket.write(list[0]); socket.write(list[1], cb)`，不做任何拷贝 | `node_modules/.pnpm/ws@8.21.3/node_modules/ws/lib/sender.js:563-570` |

> 注意：`merge`（合并拷贝）只在 `options.mask` 为真时成立，即**浏览器 → 服务器**方向。
> 因此"小帧会被拷贝"是错的：服务端发出的帧**不分大小**都是引用。慢连接/TCP 背压导致 `socket.write` 部分写入时，
> 未写完的尾巴仍引用着那块内存，下一个 tick 复写即损坏帧。

### 0.2 结论二：被复用的正是这些缓冲

| 缓冲 | 复用方式 | 证据 |
|---|---|---|
| `session.outbound`（每会话一块 `LIMITS.maxFrameBytes`） | 每 tick 重写并 `subarray` 发送 | `packages/server/src/session.ts:102`、`session.ts:121,227,252` |
| `room.broadcastBuffer`（每房间一块） | 被 matchState、事件帧、聊天帧**共用** | `packages/server/src/room.ts:119`、`room.ts:507`（事件）、`room.ts:602`（matchState）、`session.ts:343`（聊天） |
| 快照帧 | `sendSnapshot` 每 tick 重写同一块 `session.outbound` 后发送 | `packages/server/src/room.ts:522` |

证据里 `snapshotBytesMax = 482`、`matchState` 帧（含昵称）通常在 100–200B、聊天帧最长 64B+头——
都在"会被直接 `socket.write` 引用"的范围内。

### 0.3 结论三：没有任何背压控制，慢客户端无界吃内存

`ws-adapter.ts` 的 `send` 只看 `readyState`，不看 `socket.bufferedAmount`，也没有队列上限或断开策略
（`packages/server/src/transport/ws-adapter.ts:44-54`），`Transport` 接口也没有任何"积压"概念
（`packages/server/src/transport/types.ts:4-19`）。一个不读 socket 的客户端会让 Node 的写缓冲持续增长直到 OOM，
且没有任何指标能看到。

### 0.4 影响面

- **偶发、难复现**：只在背压时损坏，本机压测（4 个健康连接）几乎不会触发；线上弱网客户端会表现为
  "客户端偶发 decode 失败 / 快照错乱 / 玩家瞬移"，而服务器日志一切正常。
- **与 O02 的交互**：O02 让 tick 更准时，但每 tick 仍然复写同一块内存，风险不变。
- **与 O05 的交互**：自适应快照率、增量编码都建立在"send 之后缓冲可以被改写"这一假设上——不先修 O03，O05 的改动会**放大**风险。

## 1. 目标

本步骤结束后，`Connection.send` 的语义是**"发送即交出所有权"**：

1. 实现方必须在返回前把帧内容拷进自有（池化）缓冲，发送完成后再回收；
2. 调用方（`room.ts` / `session.ts`）在 `send` 返回后**可以立即改写**源数组，线上字节不受影响；
3. 慢客户端有界：积压超过 `LIMITS.maxBufferedBytes` 时计数并按策略断开，绝不无界增长；
4. 有一条可复现的测试证明"send 后改写源数组，接收侧字节不变"，以及一个能制造背压的探针模式。

判据：`tools/probe.mjs --slow` 场景下，服务器 RSS 有界（增长 <1MB/分钟）、
`ac_slow_client_drops_total` 增长、且客户端侧收到的每一帧都能完整解码（`decodeFailures === 0`）。

## 4. 任务清单

- [ ] 1. `send-queue.ts`（新建）：
  ```ts
  export interface SendQueue {
    readonly queuedBytes: number;
    readonly drops: number;
    send(frame: Uint8Array, write: (chunk: Uint8Array, done: () => void) => void): void;
    clear(): void;
  }
  export function createSendQueue(maxBytes: number, bufferBytes: number): SendQueue;
  ```
  实现：`frame` 先 `copyInto(pooledBuffer, frame)`；`write(view, done)`；`done` 里归还缓冲（O(1) 环形池）；
  `queuedBytes + frame.length > maxBytes` 时 `drops += 1` 并**不排队**（返回后由调用方决定断开/丢弃）。
- [ ] 2. `types.ts`：`Connection` 增加 `readonly bufferedAmount: number`；`send(frame)` 的 JSDoc 写明
  "实现必须在返回前拷贝或持有独立所有权；调用方可以立即改写 `frame`"。
- [ ] 3. `ws-adapter.ts`：每个连接一个 `createSendQueue(LIMITS.maxBufferedBytes, LIMITS.maxFrameBytes)`；
  `send` → `queue.send(frame, (chunk, done) => socket.send(chunk, { binary: true }, done))`；
  `bufferedAmount` = `queue.queuedBytes + socket.bufferedAmount`；
  当 `queue.drops > 0` 且 `bufferedAmount > 2 × maxBufferedBytes` → `socket.close(1013, 'slow client')` 并计数；
  `close`/`error` 时 `queue.clear()`（防止池泄漏）。
- [ ] 4. `memory-adapter.ts`：`send` 改成 `toClient(link, frame.slice())`（同步语义不变，但断开共享内存）；
  `bufferedAmount` 返回 0（内存适配器无真实背压，注释写明）。
- [ ] 5. `metrics.ts`：`slowClientDrops`、`sendQueueBytes`（gauge 由 `transport` 聚合，参考现有 `oversizedFrames` 的可选字段模式：`packages/server/src/transport/types.ts:18` 与 `packages/server/src/http.ts:64-72`）。
- [ ] 6. `tools/probe.mjs`：新增 `--slow` 模式——正常 join 与发命令，但**暂停读取** socket（`socket.pause()`，不 attach 数据消费者或只计数不解码），持续 `--duration` 秒后打印：服务器 RSS 增量、`ac_slow_client_drops_total` 增量、本连接是否被 1013 断开。
- [ ] 7. 测试：
  - `send-queue.test.ts`：①`send` 后改写源数组 → 回调收到的字节与发送时一致；②池容量用尽 → 复用而非新分配（断言同一 `Uint8Array` 对象被复现）；③超过 `maxBytes` → `drops` 增长且不入队；④`clear()` 后 `queuedBytes === 0`。

## 5. 冻结契约

```ts
// packages/shared/src/net/protocol.ts → LIMITS 新增
maxBufferedBytes: 262144,   // 单连接出站积压上限（字节）；超过 2 倍时按 1013 断开

// packages/server/src/transport/types.ts
export interface Connection {
  readonly id: number;
  readonly remote: string;
  readonly closed: boolean;
  /** 当前未写完成的出站字节数（队列 + socket 缓冲）。 */
  readonly bufferedAmount: number;
  /** 交出 frame 的所有权：实现必须在返回前拷贝或持有独立所有权；调用方可立即改写 frame。 */
  send(frame: Uint8Array): void;
  close(code?: number, reason?: string): void;
  onMessage(handler: FrameHandler): void;
  onClose(handler: CloseHandler): void;
}
```

| 冻结项 | 值 / 定义 |
|---|---|
| 断开码 | `1013`（try again later）= 慢客户端被断开；与既有 `1008`（策略）/`1009`（帧过大）/`1002`（协议不符）并列，不得复用 |
| 指标名 | `ac_slow_client_drops_total`（counter，帧因积压被丢弃的次数）、`ac_send_queue_bytes`（gauge，所有连接积压字节和） |
| 拷贝点唯一性 | 全仓库只有 `send-queue.ts` 负责"拷贝进自有缓冲"；`room.ts`/`session.ts` 继续复用缓冲，语义由 `Connection.send` 契约保证 |
| 池上限 | 每连接池容量 = `2 × LIMITS.maxFrameBytes`（即 16KiB），超出即视为 `drops` |
| 协议 | 不涉及（帧内容与 opcode 不变） |

## 8. 风险与回滚

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 拷贝引入每帧分配，抵消收益 | soak 的 RSS 斜率上升、GC 次数上升 | 池化 + 环形回收（O(1)）；池大小固定为 `2 × maxFrameBytes`，不随负载增长 |
| 队列增加发送延迟，手感变差 | 压测 `snapshotArrivalJitterP95Ms` 上升 | 队列只在写未完成时排队（正常情况即写即回收）；`maxBufferedBytes` 远大于单帧（256KiB vs 8KiB） |
| 误伤移动端弱网客户端（正常慢也断开） | 线上 `ac_slow_client_drops_total` 长期非零但客户端健康 | 高水位设为 `2 × maxBufferedBytes` 才断开；先只计数不处置，观察一个版本后再启用断开（可在 O10 调整为门槛） |
| 内存适配器行为变化导致既有集成测试失败 | `pnpm --filter @ac/server test` 出现快照/事件断言失败 | 内存适配器只加 `.slice()`，语义同步，不动顺序与分片；若失败按 §6 #1 定位 |
| 回滚目标 | — | 回滚 = `git revert` 本次提交（transport 三文件 + metrics + probe + docs），恢复 `send` 直传；无协议变更、无数据迁移 |
