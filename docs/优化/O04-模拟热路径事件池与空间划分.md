# O04 模拟热路径事件池与空间划分

> 里程碑：O4 ｜ 预估：1.5 会话（a/b 两块，见 §4） ｜ 上游移交物：HANDOFF-O03

## 0. 现状与不足（证据）

本步处理**模拟内核的每 tick 常数**：分离与邻居聚集都是 O(n²)，事件每 tick 新建，计数/排序/净化各自重复了一遍。
这些成本在 4 人 60 羊的满编局里直接决定单 tick 工作量——也就是 O02 引入的 `LIMITS.roomTickBudgetMs = 8` 能不能守住。

### 0.1 结论一：实体分离是 O(passes × n²)，且每对都做两次查表

| 事实 | 证据 |
|---|---|
| 双层循环 + 每对 `getEntity` 两次 + `radiusOf` 两次 + `Math.sqrt` | `packages/shared/src/sim.ts:210-249` |
| 每个 pass 之后又全量跑一遍 `collideStatic` | `packages/shared/src/sim.ts:244-249` |
| `separationPasses = 1`（上调即线性放大成本） | `packages/shared/src/config/entity.ts:21-22` |
| `getEntity` 每次带边界检查 | `packages/shared/src/world.ts:167-174` |
| 规模 | 4 玩家 + 60 羊 = 64 实体 → 2016 对/次，20Hz 下约 4 万次配对判定/秒 |

### 0.2 结论二：邻居聚集每羊全扫全部实体，且"最近 12 个"实际是"最先遇到的 12 个"

| 事实 | 证据 |
|---|---|
| `gatherNeighbors` 遍历 `world.activeIds` 全部实体，只按距离半径过滤 | `packages/shared/src/ai/flocking.ts:75-92` |
| 容量满即丢弃（`addNeighbor` 里 `if (neighbors.count >= neighbors.capacity) return`） | `packages/shared/src/ai/flocking.ts:47-60`（容量检查在 :54）、容量 12（`packages/shared/src/config/sheep.ts` 的 `maxNeighbors: 12`） |
| 规模 | 60 羊时每个羊 63 次距离计算 → 约 3780 次/tick |
| 行为影响 | 丢弃与距离无关，只与 `activeIds` 顺序（id 升序）有关 → 羊多时最近的邻居可能被丢掉，flock 转向依赖 id，属**正确性**问题而非仅性能问题 |

### 0.3 结论三：每 tick 事件对象全部分配

| 事实 | 证据 |
|---|---|
| `pushEvent` 内 `createSimEvent()` 新建对象 | `packages/shared/src/combat/resolve.ts:184-205`（`createSimEvent()` 调用在 :195）、`packages/shared/src/world.ts:103-105` |
| 另一处直接字面量 push | `packages/shared/src/ai/sheepAttack.ts:30-42` |
| 每 tick 开头 `world.events.length = 0` 丢弃引用 | `packages/shared/src/sim.ts:44` |
| 典型事件量 | 霰弹枪 8 pellet（`packages/shared/src/config/weapons.ts:53`）每次命中一条 `playerHit`；`reviveProgress` 按 5% 步进最多 20 条/人；每次击杀一条 `sheepKilled` |

### 0.4 结论四：射线路径有每调用数组分配（量级小，属清理项）

| 事实 | 证据 |
|---|---|
| `rayVsAabb` 每次调用新建 4 个数组 | `packages/shared/src/combat/raycast.ts:136-139` |
| `traceRay` 对全部活动实体做胶囊求交，无廉价早退 | `packages/shared/src/combat/resolve.ts:89-160` |
| 量级（诚实标注） | 每次 `traceRay` 4 个数组；霰弹枪一次开火 8 pellet → 32 个数组/次开火，射速下约 40 个数组/秒——**不是瓶颈**，本步一起清掉是为了让 §4 的零分配断言在整条热路径上成立 |

### 0.5 结论五：同一遍历被写了三遍，每 tick 还排一次序

| 事实 | 证据 |
|---|---|
| `aliveSheepCount` 每 tick 全扫（由 `updateDirector` 调用） | `packages/shared/src/ai/director.ts:96-104,196` |

| `collectDirectorPlayerIds` 每 tick `push` + `sort`，而 `activeIds` 本就按 id 升序 | `packages/server/src/room.ts:409-419`、`packages/shared/src/world.ts:172-178` |

| soak 的 60 羊 CPU 门槛要求羊峰值 ≥40 才取样 | `tools/soak.mjs:287-295` |
| 实测羊峰值只有 22，门槛记 `not-measured` | `docs/验收报告.md` §3.3 |

## 1. 目标

本步骤结束后，模拟内核的每 tick 常数与实体数近似线性：

1. 实体分离与邻居聚集走**同一个空间网格**（cell 边长 = `SHEEP_AI.neighborRadiusM = 3m`），配对判定只发生在同格与相邻格；
2. 事件对象**零分配**（池化复用），并把"事件对象仅当 tick 内有效"写成冻结契约；
3. 邻居"最近 12 个"按距离选取，与遍历顺序无关；
4. 活动羊数只在 `stepWorld` 里数一次，director 与 metrics 共用该结果；
5. 命令净化只发生在会话边界，模拟内核信任 `Command`；
6. 建立可复现基准 `tools/bench-sim.mjs`（4 玩家 + 60 羊），SLO 与 O02 的房间预算对齐：
   **单 tick（`stepWorld` + `snapshotWorld`）p95 ≤ 8ms、p99 ≤ 12ms**，且不得比本步开工前测得的基线更慢。

## 5. 冻结契约

```ts
// packages/shared/src/sim/spatialGrid.ts
export interface SpatialGrid {
  readonly cellSizeM: number;
  readonly cols: number;
  readonly rows: number;
  readonly cellStart: Int32Array;   // 长度 cols*rows + 1
  readonly cellItems: Int32Array;   // 长度 capacity
  readonly itemCount: number;
}
export function createSpatialGrid(cellSizeM: number, capacity: number): SpatialGrid;
export function buildSpatialGrid(grid: SpatialGrid, world: World): SpatialGrid;
export function forEachNeighbor(
  grid: SpatialGrid,
  x: number,
  z: number,
  radiusM: number,
  visit: (entityIndex: number) => void,
): void;

// packages/shared/src/world.ts
export interface WorldStats {
  aliveSheep: number;   // 每 tick 由 stepWorld 写一次；director 与 metrics 只读
}

// packages/shared/src/net/protocol.ts → LIMITS 新增
eventPoolSize: 256,     // 事件对象池容量；超过容量的事件被丢弃并计 metrics.eventsDropped
```

| 冻结项 | 值 / 定义 |
|---|---|
| 网格 cell 边长 | `SHEEP_AI.neighborRadiusM = 3m`（一格即一个邻居半径） |
| 3×3 覆盖的证明 | 最大实体半径和为 king 1.6 + elite 0.6 = 2.2 < 3，故任意可能重叠（或互为邻居）的两个实体所在格的轴向索引差 ≤1 → 3×3 邻域足够 |
| `maxNeighbors` 语义 | "距离最近的 12 个"（顺序无关）；超出半径的一律不入选 |
| 事件对象生命周期 | 事件对象**仅在当 tick 内有效**：`pushEvent` 会复用池对象，消费方必须在同一 tick 内读完（服务器广播、测试断言都在 tick 内） |
| 净化职责 | 输入净化在**会话边界**（`session.ts` 的 `sanitizeCommandFields`）与客户端采样（`sampler`）；模拟内核信任 `Command`，不再夹取 |
| 射线一致性 | 网格/早退优化不得改变 `ShotTrace` 的 `hit/targetId/part/distanceM/x/y/z`（对拍断言保证） |
| 基准 SLO | 60 羊 + 4 玩家：单 tick p95 ≤ 8ms、p99 ≤ 12ms；且不得慢于本步开工前基线 |

| 6 | 基准分配口径 | `rawPerTick` / `retainedPerTick` 各一个数 | `rawPerTick` = 3 窗口最小值（`alloc.rawSamples` 全量留档），`retainedPerTick` = 全部窗口 gc 后净增长 / 总 tick 数 | 单窗口 `raw` 会被 GC 时机放大到 ±1000 B/tick，无法跨版本比较 |

## 8. 风险与回滚

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 网格化让模拟结果与旧实现不一致（分离顺序、邻居集合变化） | `determinism.test.ts` 或 `resolve.test.ts` 对拍失败；bots 的命中/击杀与基线差异大 | 分离仍在网格内按 id 升序处理配对，保持"先出现的实体先被推"的既有顺序；对拍断言先在 O04a 全绿再进 O04b |
| 事件池引入"跨 tick 读到被覆写的事件" | 客户端出现重复/错乱事件；`encodeEventFrame` 输出异常 | 事件只在 `runTick` 内被编码（同步），文档把语义写进 §5；测试断言"tick 内读取" |
| 事件池容量不足导致丢事件 | `metrics.eventsDropped > 0` | 容量 256 覆盖 4 人 × 20 条 `reviveProgress` + 命中事件；超限计数并保留日志，容量可在 §5 上调 |
| `activeIds` 升序假设被后续改动破坏 | `collectDirectorPlayerIds` 输出未排序，导演分配错位 | 加断言（`dev` 环境）+ 注释说明依赖；若需鲁棒则保留一个廉价的"已排序"检查 |
| 净化职责移交造成作弊面 | 客户端可发送越界轴/角度 | 净化在**会话边界**（服务器唯一入口）执行，覆盖所有客户端路径；bots 直连 ws 也过同一入口；`session.test.ts` 覆盖 |
| 基准脚本测的是"本机"，数字不可跨机比较 | 换机后 SLO 不达标 | 证据文件必须记录 `os.cpus()[0].model` 与 Node 版本；SLO 只对同一台机器做前后对比 |
| 回滚目标 | — | 回滚 = `git revert` 本次提交（shared/sim + shared/ai + shared/combat + server/room + tools/bench-sim），回到 HANDOFF-O03 状态；无协议与数据变更 |
