# O10 质量门与性能守门

> 里程碑：O10 ｜ 预估：1 会话 ｜ 上游移交物：HANDOFF-O09

## 0. 现状与不足（证据）

本步是**收尾与守门**：把前面九步的成果变成"回归会变红"的门禁，并把零散的技术债收敛掉。
本步不改游戏逻辑，只改门禁、脚本、CI 与若干可验证的卫生项。

### 0.1 结论一：`pnpm check` 不含体积预算与分配探针

| 事实 | 证据 |
|---|---|
| `check` 链是七步：`typecheck → lint → test → check:docs → check:assets → check:count → check:coverage` | `package.json:14` |
| 体积预算**已经实现**（构建插件里比对 `GZIP_BUDGET_BYTES = 1_500_000`），但 `check:build` 不在链上 | `packages/client/vite.config.ts:3,29-35`、`package.json:24` |
| 分配探针 `tools/check-alloc.mjs` 存在且有自己的门槛与退出码，但没有 npm 脚本入口，也不在链上 | `tools/check-alloc.mjs:14-15,108-131`、`package.json:18-24`（无 `check:alloc`） |

结论：两件已经写好的守门能力**没接进门禁**，等于不存在。

### 0.2 结论二：`--strict` 默认关闭 → 压测"跑完但不拦人"

| 事实 | 证据 |
|---|---|
| `strict: args.has('strict')`，默认 false | `tools/bots.mjs:104` |
| 退出码只在 `options.strict` 为真时才被置 1 | `tools/bots.mjs:712,1139,1153` |

结论：`node tools/bots.mjs --players 4 --minutes 5` 即使 S5.2-x 全部 FAIL 也返回 0；
在脚本/CI 里"跑过压测"不等于"性能达标"。这正是 `docs/验收报告.md` §3.2 里 FAIL 项能被长期搁置的机制原因之一。

### 0.3 结论三：仓库没有 CI

| 事实 | 证据 |
|---|---|
| 没有 `.github`（工作流目录不存在） | `ls .github` → No such file or directory |
| 所有门禁依赖人手动执行 | `package.json:14-24` |

### 0.4 结论四：覆盖率门槛只覆盖 `@ac/shared`，且只看行不看分支

| 事实 | 证据 |
|---|---|
| `include` 只列 `packages/shared/src` | `vitest.config.ts:7-9` |
| 阈值只有 `lines: SHARED_LINE_COVERAGE_THRESHOLD (80)` | `vitest.config.ts:3,12-14` |
| `check:coverage` 只跑 `--project shared` | `package.json:23` |
| 实测 shared 行 84.92%、**分支 66.25%** | `pnpm check` 的覆盖率输出（本机实测） |

结论：server 与 client 完全没有覆盖率门禁；shared 的分支覆盖率（66%）没有下限，容易被新代码悄悄拉低。

### 0.5 结论五：测试数门槛严重宽松

| 事实 | 证据 |
|---|---|
| `MIN_TESTS = 120`，实测 364 | `tools/check-test-count.mjs:4,35-41`、`pnpm check` 输出"用例数 364 ≥ 120" |

作为"防止批量丢测试"的地板，120 对 364 的现状几乎不构成约束（可以删掉三分之二的测试而门禁仍绿）。

### 0.6 结论六：卫生项（各自独立、都可验证）

| 项 | 事实 | 证据 |
|---|---|---|
| 构建产物入库 | 3 个 `tsconfig.tsbuildinfo` 被 git 跟踪，且 `.gitignore` 未忽略 | `git ls-files | grep tsbuildinfo`、`grep -n tsbuildinfo .gitignore` |
| 文档-代码漂移 | `securityChecklist()` 文案写"32 字符表"，实际 `LIMITS.roomCodeAlphabet` 长度 31 | `packages/server/src/security.ts:233`、`packages/shared/src/net/protocol.ts` 的 `roomCodeAlphabet` |
| 未实现的配置项 | `.env.example` 的 `TICK_MS` 无任何代码读取（注释里已自证） | `.env.example:21-22` |
| 接受但无效的协议入口 | `OPCODE.respawn` 在 `CLIENT_OPCODE_LIST` 里（`protocol.ts:35`），服务器接受并只计数（`session.ts:368-371`），**客户端从不发送**（`grep -rn respawn packages/client/src` 无命中） | `packages/shared/src/net/protocol.ts:28-36`、`packages/server/src/match-flow.test.ts:80-100` |
| 永远为真的字段 | `removeMember` 的 `leftMidMatch` 参数被 `void` 掉，于是所有离场记录都写 true | `packages/server/src/room.ts:230,237,244` |

### 0.7 结论七：没有任何"门禁自检"——没人证明门槛真的会失败

仓库里没有用例/脚本验证"把预算调低后 `pnpm check` 会红"。门槛写错（例如比较方向反了）不会被发现。

## 1. 目标

1. `pnpm check` 是**九步**（新增 `check:build` 与 `check:alloc`），体积与分配进入门禁；

6. 门禁自检：四个"故意破坏 → 必须变红"的实验写进证据文件。

判据：`pnpm check` 退出码 0 且输出含九步；`pnpm check:perf` 在 2 分钟 4 人场景退出码 0；

## 5. 冻结契约

```bash
# pnpm check（九步）
pnpm typecheck && pnpm lint && pnpm test && pnpm check:docs \
  && pnpm check:assets && pnpm check:count && pnpm check:coverage \
  && pnpm check:build && pnpm check:alloc

# 新增脚本
"check:alloc": "node --expose-gc tools/check-alloc.mjs"
"check:perf":  "node tools/bots.mjs --players 4 --minutes 2 --strict"
```

| 冻结项 | 值 / 定义 |
|---|---|
| `check` 步骤数 | 9；新增 `check:build`（客户端体积预算）与 `check:alloc`（稳态分配） |
| `check:perf` | 4 人 2 分钟 `--strict`；**不**并入 `pnpm check`（耗时考虑），由 CI 的 `perf` job 承担 |
| `--strict` 语义 | 默认退出码 0（不拦人）；`--strict` 时任一门槛 FAIL → 退出码 1。此语义写进脚本 help 与报告头部 |

| 测试数地板 | `MIN_TESTS = 300` |

| `leftMidMatch` | 定义 = 离场时刻 `room.phase` 属于"对局进行中"（playing / intermission） |

### 5.1 执行期差异

| # | 差异 | 理由 |
|---|---|---|
| 1 | 反向实验 ④ 的破坏方式改为「把 `S5.2-1` 的 `status` 直接置为 `'fail'`」，而不是任务 7 写的「把 S5.2-8 阈值改成 0」 | 实测发现 `tools/bots.mjs` 里每个门槛的 `status` 是**内联表达式**（如 S5.2-8 写死 `<= 5`、S5.2-1 写死 `<= 1200`），改 `limit` 字段**不会**影响判定——改 0 后仍是 `[PASS] … limit=-1`。这本身是可维护性风险，已记入证据文件 §5 |
| 2 | `--strict` 的退出码只看 `status === 'fail'`；`not-measured` 不拦人（报告里标 `NOT-MEASURED …（不拦人）`） | 冻结契约只承诺「任一门槛 **FAIL** → 退出码 1」。4 人 2 分钟场景里 `S5.2-9b`（200ms RTT 隔墙命中）无法测量，若把它也算红，§6 #2 的「`pnpm check:perf` 退出码 0」永远无法成立 |
| 3 | `shared.lines` 维持 80（不按「基线向下取整到 5 的倍数」提到 85） | §5 冻结项写的是「`shared.lines 80`（不变）」；80 ≤ 实测基线 88.91，属**更宽松**的既有门槛，不违背「门槛不得高于基线」 |
| 4 | 覆盖率基线在**加 `packages/*/src/test/**` 排除之前**测得；随后补上该排除 | 排除测试替身（如 client 的 canvas 桩）只会让覆盖率**上升**，故四条门槛仍 ≤ 基线，安全方向一致；§0.4 记载的旧基线（shared 84.92/66.25）与本次（88.91/69.65）不同，是 include/exclude 口径变化所致 |
| 5 | `docs/验收报告.md` §6 并没有「无 CI / 体积守门未接入 / 分配探针未接入」三条；对应信息在 §5「P10 §5.5 验证状态」表里 | 按实际文档结构处理：§5 表新增 CI 一行，§6 保留既有 9 条未验证项（本步不动它们的口径） |
| 6 | CI 只做**静态复核**（prettier 解析 YAML + 人工看键名/缩进），未在本机真实跑过 | 本机是 Windows 工作站，没有 GitHub runner；`pnpm lint` 的 `prettier --check .` 会解析该 YAML，等价于语法校验 |
| 7 | `.env.example` 的 `TICK_MS` 选择**注释掉**整行（`# TICK_MS=50`）而不是保留可赋值行 | 任务 5 要求「注释化并标注未实现」；注释掉可避免使用者误以为该变量生效 |
| 8 | `room.ts` 新增私有 `isMidMatchPhase(room)`，`roomLeave` 与宽限期超时回收两处都用它 | 冻结定义是「离场时刻 phase ∈ {playing, intermission}」；连带把宽限超时回收的口径统一（此前两处都硬编码 `true`） |
| 9 | 任务 6 说「波间离场为 false」，但 §5 把 `intermission` 也算「局中」 | 以 §5 为准（intermission → true），测试里的「非局中」用例取 `loading`；矛盾已记入证据文件 |

## 8. 风险与回滚

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 接入 `check:build` 后门禁变慢 | 本地 `pnpm check` 时间明显上升 | 体积校验跟着 `vite build` 走，只构建 client（秒级）；若仍慢，把 `check:build` 放到 CI 的独立 job 并保留在 `check` 链上（本步先按链上实现） |
| 覆盖率门槛设得高于基线导致门禁立刻红 | 第一次 `pnpm check` 在 coverage 步失败 | §5 强制"门槛 = 基线向下取整到 5 的倍数"，且任务 3 要求先测量后设置 |
| 移除 `respawn` 白名单影响已有客户端/测试 | `match-flow.test.ts` 或客户端报错 | 客户端从不发送该 opcode（已用 grep 证明）；测试同步更新；数值保留以免与未来 opcode 冲突 |
| CI 上环境差异（Windows 本地 vs Linux runner）导致阈值不稳 | `perf` job 在 CI 上抖动 | `perf` 门槛基于指标（不是时间），抖动影响有限；若 CI 上 `tickJitter` 类指标不稳，按 O02 的替代判据处理并在 CI job 里显式打印环境参数 |
| `leftMidMatch` 语义变更影响历史统计比较 | 报告里该字段分布变化 | 变更点写入 `docs/验收报告.md`（口径变更说明），历史数据不做回溯修改 |
| 回滚目标 | — | 回滚 = `git revert` 本次提交（package.json、CI、vitest.config、tools、server 三处卫生修改、docs）；门禁退回七步；无协议兼容风险（白名单移除只影响一个从不发送的 opcode） |
