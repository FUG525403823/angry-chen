# ADR-014：帧预算判据的测量机制（引擎自有帧循环）

- 状态：已裁决（实现随本 ADR 一起落地）
- 日期：2026-09-29
- 影响面：`client/tools/frame-bench.ps1`（`-Mechanism auto|editor|player`）、
  `client/Assets/Tests/FrameBench.cs`、`client/Assets/Scripts/Boot/FrameBenchPlan.cs`（新增，两机制共用）、
  `client/Assets/Scripts/Boot/FrameBenchPlayer.cs`（新增）、`client/Assets/Scripts/Boot/FrameBenchDriver.cs`（新增）、
  `client/Assets/Resources/FrameBenchUrpLit.mat`（新增）、
  `docs/plans-v2/client/C14-性能剖析与优化.md` §5 第 1 条与 §8 风险表、
  `docs/evidence/client-v2-frame.md`
- 相关：C14 §5/§6/§8、C15 §6（判据行格式）、ADR-011（表现层数值单一来源）、
  `client/Assets/Scripts/Core/FrameProfiler.cs` 的 `FrameBudget`（预算唯一来源，本 ADR 未改任何数字）

## 背景与证据

C14 §5 第 1 条原文把测量方法钉在 `-batchmode` 上：

```
& $env:AC_UNITY -batchmode -projectPath client -executeMethod Ac.Tests.FrameBench.Run   # 不得加 -nographics
```

计划场景基准（`FrameBenchPlan`，真装配 `GameBootstrap` + 60 羊 + 4 玩家 + 满特效，真出帧）本机实测三次：

| 机制 | `frameP95Ms` | `frameP99Ms` |
|---|---|---|
| 编辑器 `-batchmode` + 手动 `Camera.Render()` | 46.375 / 47.659 / 46.289 | 50.974 |
| 出包 player（引擎自有帧循环，关 VSync） | **4.4858 / 4.5433 / 4.3147** | **4.9969** |

同一份装配代码、同一台机器（RTX 3060 Laptop，D3D11 level 11.1），差 10 倍。归因不是推断，是量出来的：

1. **客户端自身每帧做功 P95 = 0.196 ms**（`phaseMs.workP95`：喂快照 0.0455 + `GameLoop.Frame` 0.157），
   player 机制下 0.2393 ms。45 ms 与 4.5 ms 的差不在客户端。
2. **空场景对照**：URP 空场景 1920×1080 在 `-batchmode` 下**单独就要 23.92 ms**——已经超过整个 20 ms 预算；
   同一份实现的 player 空场景地板 **3.936 ms**（P99 4.947）。也就是说 `-batchmode` 机制下**任何内容都不可能达标**。
3. **与分辨率、与被画的东西都无关**：`-batchmode` 下 640×480（53.9 ms）≈ 1920×1080（55.5 ms）；
   同一内容换内置管线 16.2 ms；且耗时随渲染次数从 15.5 ms 爬到 45.6 ms。
4. 机制解释：`-batchmode` 下引擎**没有自己的帧循环**，能拿到的只有编辑器里手动的 `Camera.Render()`，
   而它每次都把 URP 管线重建一遍。这是测量机制的固定开销，不是被测内容的表现。

结论：§5 第 1 条的"P95 ≤ 20 ms @1920×1080"在 `-batchmode` 机制下**不可验证**。上一轮的做法是**保持门禁红、
不放松预算、不换口径去凑绿**（`docs/evidence/client-v2-frame.md` 留档），本 ADR 修掉机制本身。

## 裁决

1. **判据机制改为窗口化 player**（引擎自己拥有帧循环）：关 VSync（`vSyncCount=0` + `targetFrameRate=-1`）、
   1920×1080、预热 120 帧 + 采样 600 帧、重复 3 次取中位。`frame-bench.ps1` 新增
   `-Mechanism auto|editor|player`，`auto`（默认）在 `client/Build/Windows64/` 有出包时用 player，否则回退 editor。
2. **预算一个数都不动**：`Ac.Core.FrameBudget` 仍是唯一来源（20 / 33 ms 等）。C15 §6 冻结的判据行前缀格式
   保持原样（`FRAME-BENCH PASS p95=…ms alloc=…B`），机制名与诊断读数接在其后。
3. **`-batchmode` 路径保留为诊断口径**：同一轮输出 `editorP95` / `editorVerdict`，只与自身历史比较，
   **不参与判定**。它的价值是"同机同内容的两机制对照"，不是达标依据。
4. **判 PASS 的附加不变式**（用来挡住"测了个空循环"或"软化"）：`phaseMs.engineFrames > 0`（引擎真的在出帧）、
   真实光栅证据（`pixelCoverage` 非 0 且与编辑器机制互证）、同轮空场景地板低于预算。
5. **§5 第 1 条按本 ADR 修订**：把 `-batchmode` 字样换成 player 机制，`-nographics` 的禁令**原样保留**
   （软件光栅化的数值依旧一律无效）。§8 风险表"P95 异常低（< 5ms）"的判法从"按阈值怀疑"改为
   "按机制验证"：player 机制下必须有引擎帧计数与真光栅证据支撑，否则该轮作废。

## 后果与遗留

1. **顺带暴露的产品缺陷（本 ADR 只记录，不在此修）**：呈现层材质全部走运行期
   `Shader.Find("Universal Render Pipeline/Lit")`，仓库里 0 个 `.mat` 资产、URP 全局设置也没引用它，
   于是**出包被剥离**、player 里造不出任何材质（`materialsReady=false`，基准直接 ENV 2）。
   本次的临时手段是新增 `Assets/Resources/FrameBenchUrpLit.mat` 把该 shader 打进包；
   正式修法应是把运行期 `Shader.Find` 换成对材质资产的引用，另立任务。
2. **`-server` 在出包版本里不可用**：Unity 播放器自己解析 `-server <slave_count> <ip:port>` 并在参数不合法时
   中止进程，`GameBootstrap` 的 `-server` 分支在 player 里形同不存在。基准改用环境变量
   `AC_SERVER=127.0.0.1:0`（非法端口 ⇒ 离线，与编辑器同语义）；产品侧的连接参数入口另立任务。
3. 两机制的口径偏差逐条记在 `docs/evidence/client-v2-frame.md` §7（共 18 条），含"player 无 profiler 计数器 ⇒
   分配改用同窗口 `GC.GetTotalMemory(false)` 逐帧差（两手段都得 0 B/帧）"与"引擎渲染统计时有时无时回退提交计数
   （回退方向是**少算**）"。
