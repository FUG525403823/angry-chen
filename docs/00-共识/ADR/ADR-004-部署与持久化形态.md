# ADR-004 部署与持久化形态

- 状态：已接受（M0 前）
- 生效范围：`@ac/server` 的进程形态、`MatchStore`、P10 的发布与运维

## 背景

1. 环境实测：**本机没有 docker**（`docker --version` 失败），没有 go/rustc。发布链不能依赖容器。
2. 游戏形态：1–4 人协作 PVE，好友局/局域网为主，非大规模线上服务。
3. 需要持久化的东西很少：对局结算统计与本地排行榜。没有账号、没有付费、没有跨服资产。

## 决策

### 1. 进程形态

- **单进程、单端口**：一个 Node 进程同时承载 HTTP（静态资源、健康检查、`/metrics`）与 WebSocket（游戏）。房间是进程内对象，无跨进程协调。
- 服务端**零构建产物**：直接 `tsx src/main.ts` 运行源码；dev 用 `tsx watch`。
- 生产用反向代理终结 TLS：Caddy 或 Nginx 把 `wss://` 转到本地 `ws://127.0.0.1:PORT`。提供两份配置样例（Caddyfile、nginx.conf）与 PM2 / systemd 两种守护样例。
- **Dockerfile / docker-compose 作为可选产物**交付，但因本机无 docker，**只做静态审查，不做构建验证**；文档中必须显式标注这一点，避免读者误以为已实测。

### 2. 持久化

- 定义 `MatchStore` 接口（一个缝）：`appendMatchResult(result)` / `listTopScores(limit)` / `getRecentMatches(limit)`。
- MVP 只实现 `JsonMatchStore`：追加式 NDJSON（`data/matches.ndjson`）+ 启动时读取构建内存索引。**单进程单写入者**，不做并发控制。
- 明确**不选** `node:sqlite`：本机实测可用但带 `ExperimentalWarning`，API 可能变动；MVP 的数据量（每局 1 行）用不上 SQL。
- 未来若需要查询能力，新增 `SqliteMatchStore` 适配器实现同一接口，不改调用方（缝的价值所在）。

### 3. 配置

- 12-factor 风格：全部通过环境变量注入，仓库内提供 `.env.example`。不提交任何密钥。
- 关键配置：`PORT`、`HOST`、`MAX_ROOMS`、`MAX_PLAYERS_PER_ROOM`、`TICK_MS=50`、`DATA_DIR`、`LOG_LEVEL`、`ALLOWED_ORIGINS`。
- `TICK_MS` 虽然可配，但**模拟内核只接受 50ms**；改配置只影响服务器调度，改步长需要同步改模拟常量与数值表（属于冻结契约变更）。

## 备选方案与被否决理由

| 方案 | 否决理由 |
|---|---|
| Docker 为唯一交付形态 | 本机无 docker，无法验证；会造成"文档说能跑但没跑过" |
| Node 集群 / 多进程 + Redis 房间 | 4 人局的规模完全不必要，且引入状态外置的复杂度 |
| `node:sqlite` 作为默认存储 | 实验特性，且 MVP 查询需求为零 |
| 云数据库 / 账号系统 | 超出 MVP 范围，写入路线图而非现在做 |

## 后果

- 正面：发布链极简，一条命令起服务；数据零依赖，删除目录即重置。
- 负面：`MatchStore` 是单写入者的，若未来多进程部署需换适配器；已在接口层面预留。
- 重新评估触发条件：需要跨机房间列表、需要账号与云排行、需要多房间水平扩容。
