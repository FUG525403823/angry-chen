# ADR-005 模拟缓冲所有权与活动实体表

- 状态：已接受（P02）
- 生效范围：@ac/shared 的 world.ts / snapshot.ts / sim.ts

## 背景

服务器以 20Hz 驱动 stepWorld 与 snapshotWorld，并且这两个函数同时被服务器权威步进、客户端预测步进和无头压测机器人调用。若每 tick 分配对象，V8 会在 20Hz 上反复触发新生代回收，P10 的 CPU 预算与客户端帧率都会被吃掉。

P02 实测暴露了两个具体问题：

1. resolveEntitySeparation 在 1024 个实体槽位上做 O(n²) 双层遍历（每 tick 约 52 万次迭代），node --trace-deopt 显示它在 3000 tick 内被去优化 197 次（大多为 OSR 退出），稳态仍持续产生垃圾。
2. 早期实现把快照复用池挂在 World 上，于是「调用方传入的 out」只是外壳：两个同时存在的 out 会互相覆盖，调用方无法预期自己持有的快照何时失效。

## 决策

1. **活动实体表**：世界维护 ~activeIds: EntityId[]~，始终按 id 升序稠密排列（spawnEntity 插入到有序位置，despawnEntity 移除）。模拟各阶段（命令应用、积分、静态碰撞、实体分离、快照投影）只遍历这张表，复杂度从 O(槽位数²) 降为 O(活动实体²)，且遍历顺序天然是 id 升序，跨端确定。liveCount 由该表长度派生，不再单独维护。
2. **快照缓冲归调用方**：复用池以 WeakMap 绑定在调用方长期持有的 out 实例上，world 不再持有任何投影缓冲。同一 out 跨 tick 复用同一批实体对象；不同 out 互不干扰。代价是「每 tick 新建 out」会重新分配整池（256 个对象），因此 P03 的每连接快照缓冲必须长期持有。
3. **世界只持有模拟期缓冲**：events、scratchEntities、commandScratch 属于世界内部，随世界生命周期存在，不与调用方交替使用。

## 后果

- 稳态实测：stepWorld + snapshotWorld 每 tick 新增堆字节 1.22 B、保留增长约 0、10 万 tick 内 5 次 GC 事件，约 1.23 µs/tick（4 实体）；对照组（每 tick 新建缓冲）为 379 B/tick、141 次 GC 事件。
- 后续任何「临时快照」（UI 或调试）必须自己持有 Snapshot 实例，否则会与其他消费者互相覆盖。
- 波次生成与命中判定（P06/P07）新增实体时必须走 spawnEntity，不得直接改 entities 数组，否则 activeIds 会失配。
