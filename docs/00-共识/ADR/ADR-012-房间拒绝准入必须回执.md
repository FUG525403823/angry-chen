# ADR-012 房间拒绝准入必须回执

- 状态：已接受（v2 收尾／联调阶段）
- 生效范围：`server/src/server/runtime.cpp`（Hello 路径的房间准入）、`server/src/net/handshake.hpp`（断开原因码表）、`client/Assets/Scripts/Net/Handshake.cs`（原因码表与解码上界）、`client/Assets/Scripts/Net/KeepAlive.cs`、`client/Assets/Scripts/Net/UdpTransport.cs`
- 关联：[ADR-009](ADR-009-UDP传输与协议重构.md)（报文类型与断开原因码）、[ADR-006](ADR-006-会话身份与重连令牌.md)（宽限期身份按令牌匹配）
- 依据：S10 §5.5（准入结果四态与"`playing` 阶段不得中途加入"）、S04 §5.5（断开原因码 1–7）、C15 §5 第 2 步（"4 人名额上限生效，第 5 人被拒"）

## 背景

联调实测（`build/joint/`，见 `docs/evidence/client-v2-acceptance.md` §2）：房间里已有 3 个 `ac_bot`
且第 2 局进行中（`phase = playing`）时，客户端 31ms 完成握手（`/health` 的 `connections` 由 3 涨到 4、
日志 `[joint] step1 ok session=4`），但 `/health` 的 `players` 始终是 3，客户端 5s 内
`matchStates=0`、`rows=0 phase=0` —— 玩家挂在"已连接但永远收不到 MatchState"的黑洞里。

根因在两处，缺一不可：

- `runtime.cpp` 的 Hello 路径把准入结果丢掉了：`(void)ac::room::roomJoin(...)`。
- `room.cpp` 的 `roomJoin` 会返回 `kRoomFull`（`room.sessionCount >= capacity`）或
  `kMatchInProgress`（`phase == playing`），而这两条拒绝路径**不产生任何回包**；`HelloAck` 已经发出，
  客户端只能看到"已连接"，`kJoin`（type 11）按 ADR-009 本来也不回包。

S10 §5.5 冻结的是**服务端自己的判定**（谁被拒、什么阶段被拒），没有规定"拒绝要不要告诉客户端"；
C15 §5 第 2 步却要求"第 5 人被拒"是**可观测**的判据。缺口就在这里。

## 决策

1. 断开原因码表**追加** `8 = kRoomUnavailable`（房间不可入：满员或对局进行中）。1–7 逐字不动
   （两侧同一张表，追加即可，不改写语义）。
2. Hello 路径的房间准入结果**不得丢弃**：非 `kOk` 时，先按现有流程回 `HelloAck`（握手本身成立、
   会话在册），紧接着回一帧 `Disconnect(reason = 8)`。选择"回执"而不是"静默"的理由：客户端在
   Hello 之后没有任何别的通道能得知自己被拒。
3. **拒绝的判定规则不变**（S10 §5.5 的四态、`playing` 阶段不得中途加入、满员不得进）。本 ADR 只补回执，
   不动准入策略。
4. 回执对 **Hello 重发**同样生效：§5.5 的去重会把 `HelloAck` 幂等再发一遍，准入也随之重走一遍
   （`roomJoin` 仍然拒绝），因此"在册但不在任何房间"的会话每次重发都会再收到一帧 `Disconnect(8)`，
   直到客户端放弃或会话过期。否则一帧 UDP 丢掉就等于把玩家重新挂回黑洞（这正是被修掉的那个症状）。
5. 客户端必须**保留**原因码：`KeepAlive.OnDisconnect(reason, …)` 记 `LastDisconnectReason`，
   `UdpTransport` 向外暴露；`HandshakeCodec.DecodeDisconnect` 的上界从 7 放宽到 8。展示文案统一为
   "房间满员或对局进行中"（一个码，不拆两种提示）。

## 后果

- 客户端不再干等：状态回 `Disconnected`、`DisconnectedByServer = true`、`LastDisconnectReason = 8`。
  验收第 2 步的"第 5 人被拒"从"没出现在玩家表里"升级为"收到明确回执"，判据可观测。
- 拒绝时**不回收**在册会话槽：会话槽按 S04 §5.6 的失联超时自然过期；房间名额本来就没被占用
  （准入失败发生在 `room.sessionCount += 1` 之前）。本 ADR 不引入"拒绝即回收"的新语义。
- 不新增指标与日志事件：S13 §5 的计数名单是契约（"名字即契约"，追加要同提交改清单与断言），
  `core/log.hpp` 的事件名同理。要指标时另开一次变更。
- 1–7 与 C03/S04 逐字一致这条不变量仍然成立；新增的 8 需要两侧同步（服务端 `handshake.hpp`、
  客户端 `Handshake.cs` 的解码上界）。
- **待人类复核**：全房间（4/4）与对局进行中是两种不同的玩家体验，本 ADR 只给一个码；
  如果策划要"房间已满"与"对局进行中"两种提示，需要再加一个码并同步两侧。
