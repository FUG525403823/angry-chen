# 部署清单（云服务器 / 单机 + 反代）

> 用途：把本项目部到一台公网 Linux 机器上并跑通冒烟与压测。
> 验证状态图例沿用 P10 §5.5：**已验证**（有可复现命令与输出）/ **静态审查**（无环境验证）/ **未验证**。
> 本清单中标注「静态审查」的步骤必须在真机执行后回填证据，未执行完不得对外宣称已上线。

## 0. 前置条件

| 项 | 要求 | 备注 |
|---|---|---|
| 系统 | Linux x86_64（Debian/Ubuntu 或同类） | systemd 单元样例按此写 |
| 运行时 | Node 24 + pnpm 11（corepack enable 或 npm i -g pnpm） | 仓库 engines 以 package.json 为准 |
| 网络 | 出网（装依赖、拉代码、签 TLS 证书） | 无出网只能走上传产物，构建物含平台相关二进制，成本高 |
| 端口 | 80 / 443 对公网开放；8787 只对本机开放 | 8787 不要暴露公网 |
| 域名 | 建议有（wss 与安全上下文需要 TLS） | 只有 IP 时可用自签证书验证，浏览器会告警 |
| 权限 | sudo（装 systemd 单元、写 /etc） | 无 sudo 时用 PM2 + 用户态 Caddy，见步骤 7 备选 |

## 1. 记录机器信息（先做，写进交付报告）

```bash
cat /etc/os-release | head -3; uname -m; nproc; free -m | head -2; df -h / | tail -1
```
期望：拿到发行版、架构、核数、内存、磁盘。4 人局 + 60 羊的实测 CPU 均值仅 2.02%（压测机），1 vCPU / 1 GB 起步够用。

## 2. 安装运行时

```bash
sudo apt-get update && sudo apt-get install -y curl git ca-certificates
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash - && sudo apt-get install -y nodejs
sudo corepack enable && corepack prepare pnpm@11 --activate
node -v && pnpm -v
```
期望：node -v 输出 v24.x，pnpm -v 输出 11.x。失败处置：corepack 被墙时改用 npm i -g pnpm@11。

## 3. 建用户与目录

```bash
sudo useradd -r -m -d /srv/angry-chen -s /bin/bash angrychen || true
sudo install -d -o angrychen -g angrychen -m 0750 /var/lib/angry-chen
sudo install -d -o angrychen -g angrychen -m 0750 /var/log/angry-chen
sudo install -d -o angrychen -g angrychen -m 0755 /srv/angry-chen
```
期望：目录就位。注意 DATA_DIR 必须用绝对路径——默认 ./data 会落到工作目录，systemd 下容易写不进去。

## 4. 取代码并安装依赖

```bash
sudo -u angrychen git clone https://github.com/FUG525403823/angry-chen.git /srv/angry-chen
cd /srv/angry-chen && sudo -u angrychen pnpm install --frozen-lockfile
git -C /srv/angry-chen describe --tags
```
期望：安装无报错，describe 输出与要发布的 tag 一致（当前最新为 M9）。失败处置：先 git fetch --tags 再看；锁文件与 package.json 不一致说明分支不对。

## 5. 质量门（真机复跑，不要跳）

```bash
cd /srv/angry-chen && pnpm check
```
期望（我方最后一次实测）：58 测试文件 / 364 用例全通过，typecheck + eslint + prettier + check:docs + check:assets + check:count(≥120) + check:coverage（shared 行覆盖 84.92% ≥ 80%）。
失败处置：覆盖率门槛在低配机上偶发超时，先重跑一次；仍失败就不要继续部署，回报现象。

## 6. 构建客户端

```bash
cd /srv/angry-chen && pnpm build:client
du -sh packages/client/dist && ls -l packages/client/dist/assets | head
```
期望：构建成功，JS gzip 合计 ≤ 1.5 MB（我方实测：index 41.35 kB + three 分包 135.49 kB = 176.84 kB）。体积断言已内置在 packages/client/vite.config.ts，超限会直接失败。

## 7. 进程守护（样例都是静态审查，真机必须实测）

### 7a. systemd（有 sudo 时首选）

```bash
sudo cp deploy/angry-chen.service /etc/systemd/system/angry-chen.service
sudo cp .env.example /etc/angry-chen.env && sudo chmod 600 /etc/angry-chen.env
sudo editor /etc/angry-chen.env
sudo systemctl daemon-reload && sudo systemctl enable --now angry-chen
systemctl status angry-chen --no-pager | head -12
```
按步骤 8 修改 /etc/angry-chen.env 的值。单元要点（已在 deploy/angry-chen.service 写好）：User=angrychen、WorkingDirectory=/srv/angry-chen、EnvironmentFile=/etc/angry-chen.env、ExecStart=/usr/bin/pnpm --filter @ac/server run start、Restart=on-failure、KillSignal=SIGTERM、TimeoutStopSec=10。
**必须实测**：sudo systemctl stop angry-chen 后检查日志最后一行是优雅退出（SIGTERM 路径在 Git Bash 下无法验证，属静态审查）。

### 7b. PM2（无 sudo 时用）

```bash
npm i -g pm2 && pm2 start deploy/ecosystem.config.cjs && pm2 save && pm2 logs angry-chen-server --lines 50
```
注意：PM2 不读 .env，要么在 deploy/ecosystem.config.cjs 的 env 块里写全变量，要么启动前 set -a && . ./.env && set +a。

## 8. 环境变量（/etc/angry-chen.env 或守护进程 env 块）

| 变量 | 生产建议值 | 说明 |
|---|---|---|
| HOST | 127.0.0.1（有反代）/ 0.0.0.0（无反代直连） | 无反代直连必须 0.0.0.0，否则只有本机能连（ADR-007） |
| PORT | 8787 | 反代回源端口 |
| DATA_DIR | /var/lib/angry-chen | 战绩 matches.ndjson 与 reports/<matchId>.json |
| LOG_LEVEL | info | 单行 JSON，字段 ts/level/evt/room/tick/pid/detail；排障时临时 debug |
| ALLOWED_ORIGINS | https://你的域名（走反代）/ 不设置（同源单进程托管） | 浏览器来源白名单；同源托管时不要设置（ADR-007）；* 仅限本机开发 |
| CLIENT_DIST | 留空（自动探测 packages/client/dist） | 静态资源目录；off 关闭静态托管（ADR-007） |
| MAX_ROOMS | 64 | 上调前先确认内存与单核预算 |
| MAX_PLAYERS_PER_ROOM | 4 | 玩法为 1–4 人协作 |
| TICK_MS | 50 | 当前代码不读该变量，实际步长按 SERVER_TICK_MS=50 |

## 9. 反向代理与 TLS

```bash
sudo cp deploy/Caddyfile /etc/caddy/Caddyfile && sudo editor /etc/caddy/Caddyfile
sudo systemctl reload caddy && curl -sS -o /dev/null -w "%{http_code}\n" https://你的域名/health
```
要点：静态资源也可以完全由 Node 进程托管（ADR-007）——`pnpm serve` + `HOST=0.0.0.0` 就是「一个地址可玩」，反代只在需要 TLS/域名时加；走反代时静态资源指向 /srv/angry-chen/packages/client/dist；/health、/metrics、/api/* 与 WebSocket 升级转发到 127.0.0.1:8787（Caddy 自动处理升级；nginx 需要 Upgrade/Connection 头，样例见 deploy/nginx.conf）。只有 IP 时用自签证书或 tls internal，浏览器会有告警。

## 10. 冒烟（未验证项，真机第一次执行）

```bash
curl -s http://127.0.0.1:8787/health; echo
curl -sI http://127.0.0.1:8787/ | head -1          # 200 + text/html（Node 自带静态托管，ADR-007）
curl -s http://127.0.0.1:8787/metrics | grep -E "ac_(sheep_alive|wave_current|spawns_total|grace_active|matches_finished_total|corrupt_lines_total)"
pnpm smoke                                              # 与 CI 同一份跨平台自检：静态托管 + /ws 握手（需先 pnpm build:client）
sudo ss -lntp | grep -E ":8787|:443|:80"
journalctl -u angry-chen -n 20 --no-pager
```
期望：/health 返回 200 且 JSON 带状态字段（以实际输出为准）；/metrics 能看到上述指标名；端口只有 443/80 对公网、8787 仅本机；日志是单行 JSON，且没有每 tick 常态日志。

## 11. 真机压测（用真实网络数字替代压测机数字）

```bash
cd /srv/angry-chen
node tools/bots.mjs --players 4 --minutes 5 --latency 80 --jitter 20 --loss 0.01
node tools/bots.mjs --players 4 --minutes 5 --latency 200
node tools/soak.mjs --minutes 5
node tools/report.mjs
```

soak 时间允许时再跑 --minutes 30；report 生成验收报告骨架，阈值判定写进 docs/evidence/。对照 P10 §5.2 阈值判定，不允许为了收尾放宽阈值：

## 12. 备份、回滚与运维

- 备份：DATA_DIR/matches.ndjson 与 DATA_DIR/reports/ 每日打包（战绩是唯一持久数据，删目录即重置）。
- 回滚：git fetch --tags && git checkout 上一个 tag && pnpm install --frozen-lockfile && pnpm build:client && sudo systemctl restart angry-chen；回滚不改协议与玩法，数据文件可继续用。
- 日志轮转：给 journald 或 /var/log/angry-chen 配 logrotate，避免长跑打满磁盘。
- 扩容路径（写进手册而非现在实现）：单机 + 反代 + 日志 + /metrics 为上限；再往上走多进程分房间（需把房间数上限与路由抽出来）。更多故障条目见 docs/运维手册.md。

## 13. 安全核对（上线前逐条打勾，位置见 P10 §5.4）

1. 服务端权威：客户端无伤害/无击杀能力（P06 权威性测试）。
2. 单帧上限 8192 字节，超限断开；3. 频率限制 60 msg/s，3 次超限断开；4. opcode 白名单。
5. 输入字段范围校验；6. 姿态/速度/加速度反作弊；7. 昵称与聊天净化。
8. 房间码熵：文档写 32 字符表 4 位，实现实际为 31 字符（31^4 = 923521，仍可接受但低于文档所述约 10^6），另有失败重试节流。
9. ALLOWED_ORIGINS 来源白名单；10. 仓库无密钥、.env 被忽略、日志不打印昵称以外个人信息。
11. 未捕获异常记日志且进程保持可用；12. 运行时依赖仅 three + ws + tsx。

生产加固建议（当前未实现，属已知缺口）：反代层加限流与连接数上限；/metrics 加访问控制或只对 127.0.0.1 开放；没有账号体系——任何人拿到 URL 都能进房，测试期建议用防火墙白名单或不公开域名，并避免把房间码贴在公开渠道。

## 16. 已知不达标与风险（不可掩盖）

1. tick 抖动 P95 12.85 ms（阈值 ≤8 ms）与硬纠正 523.34 次/分钟/人（阈值 ≤5）未达标；后者语义上是压测端在模拟丢包下的重放计数，不等于真实预测缺陷，但上公网高 RTT 后很可能更明显，建议作为上线后第一优先排查项。
2. 30 分钟全量 soak 未跑（只跑过 5 分钟）。
3. 游戏从未在浏览器中被真正玩过：AC-01/02/06/07/09 全部未执行。
4. 没有账号体系与公平性保障（无登录、无服务器侧匹配限制），只适合朋友间自建局。
