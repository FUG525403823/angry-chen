## 5. 冻结契约
### 5.1 包头（逐字复述 ADR-009，小端）
| 头 | 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 通用包头（8B） | 0 | `version` | u8 | 协议版本，v2 = `1`；不匹配回 `Disconnect(reason=1)` |
| 通用包头 | 1 | `type` | u8 | 1 Hello / 2 HelloAck / 3 Resume / 4 Command / 5 Snapshot / 6 Event / 7 KeepAlive / 8 Disconnect / 9 Fragment |
| 通用包头 | 2 | `flags` | u16 | bit0=reliable，bit1=moreFragments，bit2=ackOnly |
| 通用包头 | 4 | `session` | u16 | 会话短 ID；握手前为 0 |
| 通用包头 | 6 | `seq` | u16 | 每通道独立递增（回绕 mod 2^16） |
| 可靠扩展头（12B） | 8 | `msgId` | u32 | 可靠消息唯一 ID，接收侧去重 |
| 可靠扩展头 | 12 | `ackBase` | u32 | 已收到的最大 `msgId` |
| 可靠扩展头 | 16 | `ackBits` | u32 | `ackBase` 之前 32 位位图（bit i = `ackBase-1-i` 已收到） |
| 分片头（4B） | +0 | `fragId` | u16 | 同一逻辑消息的分片组 ID |
| 分片头 | +2 | `fragIndex` | u8 | 分片序号（0 起） |
| 分片头 | +3 | `fragCount` | u8 | 分片总数，上限 8 |

- `payloadOffset = 8 + (flags.reliable ? 12 : 0) + (flags.moreFragments ? 4 : 0)`；**可靠扩展头恒定在前、分片头在后**（两个 flag 同时置位时不得交换顺序）。
- 通道与类型映射：`SnapshotChannel` = type 5（不可靠，无扩展头）；`EventChannel` = type 6（reliable）；`CommandChannel` = type 4（reliable）；KeepAlive = type 7 且 `flags = reliable|ackOnly`、载荷 0 字节、不进重传队列。
- 分片包 = `type 9` + 分片头 + 原始包字节的切片；快照分片不可靠（`moreFragments`），事件分片可靠（`reliable|moreFragments`）。
- 预算：单包载荷 ≤ 1200 字节（含头）；快照 ≤ 2048 字节；稳态快照 ≤ 1228 字节；80m 场地下实体记录上限 255/帧，移除上限 255/帧。

### 5.2 命令载荷（type 4，固定 14 字节）
| 偏移 | 字段 | 类型 | 取值 |
|---|---|---|---|
| 0 | `moveX` | i8 | 量化轴，-127..127（1 = 全速右移） |
| 1 | `moveY` | i8 | 量化轴，-127..127（1 = 全速前进） |
| 2 | `yaw` | u16 | 角度单位，0..65535 = 0..2π |
| 4 | `pitch` | u16 | 角度单位，俯仰 |
| 6 | `buttons` | u8 | bit0 fire / bit1 reload / bit2 interact / bit3 ready / bit4 sprint / bit5 jump / bit6 rage / bit7 switchWeapon |
| 7 | `switchTo` | u8 | 0 pistol / 1 rifle / 2 shotgun |
| 8 | `seq` | u16 | 命令序号（与包头 `seq` 同值，供服务器去重与客户端对账） |
| 10 | `clientTick` | u32 | 客户端已知的最新权威 tick |

命令包总长 = 8 + 12 + 14 = 34 字节；`priority` 字段不设（积压策略由通道决定：只发最新、积压 > 2 丢中间）。

### 5.3 差分快照编码顺序（type 5，不可靠）
| 段 | 长度 | 内容 |
|---|---|---|
| header | 8B | `type=5`，`flags=0`，`session`，`seq` |
| tick | 4B | u32，本快照所属模拟 tick |
| serverTimeMs | 4B | u32，相对对局开始的毫秒 |
| lastAckedSeq | 2B | u16，客户端最近确认的命令序号（回显给客户端做对账） |
| baselineTick | 4B | u32，差分基线 tick；`0` = 全量（客户端清空镜像） |
| 实体块 | 1B + 15B×n | `count` u8（≤255）后接实体记录，按 `EntityId` 升序 |
| 移除列表 | 1B + 2B×m | `removedCount` u8（≤255）后接被移除 `EntityId` u16，升序 |
| 事件块 | 1B + Σ | `eventCount` u8 后接本 tick 事件（§5.4 的条目编码，含 `eventId`） |

实体记录（15 字节，与 v1 记录同宽）：`id` u16、`kindFlags` u8（bit0-1 = kind：0 player/1 sheep/2 projectile/3 pickup，bit2-7 = flags：downed=1、rageMode=2、reloading=4、charging=8、fading=16、idle=32）、`x`/`y`/`z` i16（厘米）、`yaw` u16、`pitch` u16、`hpRatio` u8、`state` u8。
进入实体块的判据：基线中不存在该 `EntityId`，或该 id 的 15 字节记录与基线字节不同；移除列表只列“基线存在且本帧不再存在”的 id。

### 5.4 事件块与事件类型（type 6 EventChannel 用同一张表）
事件帧载荷：`tick` u32、`count` u8、`count` × 条目；条目 = `eventId` u32 + `type` u8 + 类型载荷。
| type | 名称 | 载荷字段 | 载荷字节 | 条目总长 |
|---|---|---|---|---|
| 1 | `playerHit` | `subjectId` u16、`targetId` u16、`value` u16（伤害）、`flags` u8（headshot=1/downed=2/killed=4） | 8 | 12 |
| 2 | `sheepKilled` | `targetId` u16、`subjectId` u16、`kind` u8（0 grunt/1 ram/2 elite/3 king） | 6 | 10 |
| 3 | `waveStart` | `wave` u8、`budget` u16 | 4 | 8 |
| 4 | `waveClear` | `wave` u8、`elapsedMs` u32 | 6 | 10 |
| 5 | `playerDowned` | `subjectId` u16 | 3 | 7 |
| 6 | `reviveProgress` | `targetId` u16、`subjectId` u16、`ratio255` u16 | 7 | 11 |
| 7 | `reviveDone` | `targetId` u16、`subjectId` u16 | 5 | 9 |
| 8 | `rageActivated` | `subjectId` u16、`durationMs` u16 | 5 | 9 |
| 9 | `matchEnded` | `reason` u8、`wave` u8、`durationMs` u32 | 7 | 11 |
| 10 | `phaseChange` | `phase` u8（0 lobby/1 loading/2 playing/3 intermission/4 ended）、`wave` u8、`intermissionMs` u16 | 5 | 9 |

`eventId` 从 1 起单调递增、全局唯一、永不重用；重复 `eventId` 必须被接收侧静默丢弃（幂等键）。type 2–10 的数值在 [ADR-009](../../00-共识/ADR/ADR-009-UDP传输与协议重构.md) 的分层之外由本表冻结，编码实现不得自行增删或改号。

### 5.6 解码失败原因（不抛异常，一律返回值）
`enum class DecodeFailure { kOk, kTruncated, kBadVersion, kBadType, kBadLength, kBadValue, kBadSession, kUnknownEvent, kDuplicateEventId }`；`DecodeResult<T> = { ok, failure, value }`。解析失败的消息由调用方计数并丢弃（工程约定 §7），不得让进程退出。

## 8. 风险与回滚
| 风险 | 触发信号 | 对策 |
|---|---|---|
| 与 ADR-009 字段表漂移 | `hello.hex`/`command.hex` 解码字段与表不符 | §5.1 逐字复述 ADR-009；任何字段变更先改 ADR 再改代码再重生成 fixture |
| 双扩展头顺序未冻结导致双端不一致 | 客户端解出的 `command.hex` 字段错位 | §5.1 已冻结“可靠头在前、分片头在后”与 `payloadOffset` 公式，两侧共同实现 |
| fixture 与实现同改（自证循环） | fixture 被顺手改掉以迁就实现 | fixture 变更必须同时给出 ADR 变更或 v1 侧对照证据，评审时单项检查 |
| 事件编号与 v1 事件语义冲突 | 客户端 HUD 事件对不上 | 编号沿用 v1 `EVENT_TYPE`（1–9），只新增 10 `phaseChange`；改动走 ADR |
| 解码器出现越界读 | fuzz 用例崩溃或 ASan 报错 | 所有读取先做长度前置检查，读函数返回 0 而非解引用 |

回滚目标：`HANDOFF-S02`——删除 `server/src/net/**`、`server/tests/codec_test.cpp` 与 `server/tests/fixtures/**`；核心内核与构建门不受影响，`node tools/check-docs.mjs` 仍全绿。
