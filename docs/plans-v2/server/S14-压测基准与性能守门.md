# S14 压测、基准与性能守门
> 里程碑：MS14 ｜ 预估：1 人日 ｜ 上游移交物：HANDOFF-S13

## 1. 目标

本步结束后，"服务器够快吗"不再靠观感：一个无头机器人客户端能生成 4 人 + 60 羊的合成负载、一个基准程序能给出单 tick 与编码段的绝对值、一个守门程序按 §5 的门槛表判定并输出机器可读报告，且该判定接入 CI（`server-perf` job）——门槛一旦回归变红，流水线立刻变红。门槛口径继承 v1 守门脚本 `bots.mjs`、`soak.mjs` 与 `O10 质量门与性能守门`；编译纪律见 [ADR-010](../../00-共识/ADR/ADR-010-跨语言确定性与对拍.md)。

## 5. 冻结契约

门槛数值表（`ac_gate` 的判定即此表；改表必须先改本节）：

| # | 门槛 | 值 | 采样方式 / 计数点 |
|---|---|---|---|
| G1 | 4 人 + 60 羊，**单核占用** | **< 30%** | 进程 CPU 时间增量 ÷ 墙钟增量 × 100；1s 周期；去掉前 15s 预热后取**全部样本**（场景总长 120s）的**均值**（P95 只记录不判定） |
| G2 | 每客户端出站带宽 | **≤ 40 KB/s** | 出站 UDP **载荷字节**（不含 IP/UDP 头），按 (client, channel) 分桶，1s 窗口取最大值 |
| G3 | 快照帧字节 P95 | **≤ 1228 B** | 最近 **4096** 个快照帧样本，最近秩法 P95 = `sorted[ceil(0.95 × N) − 1]` |
| G4 | 单快照帧字节 | **≤ 2048 B** | 全程最大值 |
| G5 | 硬纠正 | **≤ 5 次/分钟/人** | `ac_hard_correct_total` 差值 ÷ 分钟数 ÷ 在线人数 |
| G6 | tick 调度误差 P95 | **≤ 8 ms** | 口径同抖动定义；本机定时器粒度 > 8 ms 时用替代判据：前/后 1/3 P95 差 ≤ **2 ms** 且 `|ac_sim_drift_ms| ≤ 50 ms` |
| G7 | RSS 增长斜率（5 分钟 soak） | **< 1 MB/分钟** | 1s 采样线性回归斜率 |
| G8 | 事件丢弃 / 未捕获异常 / tick 跳过 | **= 0** | `ac_events_dropped_total`、日志 `error.uncaught` 计数、`ac_tick_skips_total` |

压测场景（`gate.cpp` 的三个 `--scenario`，参数冻结）：

| 场景 | 参数 | 用途 |
|---|---|---|
| `gate-4p2min` | 4 机器人 + 60 羊预算、2 分钟、`--seed 20260101`、默认档位 | CI 的 `server-perf` 快速判定（G1–G6、G8） |
| `soak-4p5min` | 4 机器人 + 60 羊、5 分钟、每 10s 采样 | G7 与房间回落（结束后房间数回 0） |
| `latency-200` | 在 `gate-4p2min` 上注入 RTT 200ms ± 20ms、丢包 1% | 隔墙命中 = 0（权威性）与回滚 `clamped` 比例 |

失败判定与报告 JSON（`build/server-perf.json`，字段冻结）：

`{ tool, version, scenario, seed, buildType, compiler, host, startedAt, durationSec, verdict, exitCode, thresholds:[{ id, label, measured, limit, unit, status }], metrics:{ cpuMeanPct, cpuP95Pct, bytesPerClientMaxKbps, snapshotBytesP95, snapshotBytesMax, hardCorrectPerMinPerClient, scheduleErrorP95Ms, simDriftMsMax, rssSlopeMbPerMin, eventsDropped, tickSkips, uncaughtExceptions } }`

| 冻结项 | 值 |
|---|---|
| `status` 取值 | `pass` / `fail` / `not-measured` |
| 退出码 | 任一 `fail` → **1**；只有 `not-measured` → **0**（并在报告头标注不拦人） |
| 反向自检 | `threshold_test.cpp` 必须证明"把 G3 阈值临时改成 0 → 退出码 1"，即门槛真的会拦人 |
| CI job | `server-perf`（三 job 结构 `quality`/`server`/`server-perf` 中的第三个）：`needs: quality`、`timeout-minutes: 20`、上传 `build/server-perf.json` 为 artifact |
| 编译纪律 | 三个工具目标用 Release 优化，禁 `-ffast-math`、`-march=native`，基准段不得含文件 IO |

## 8. 风险与回滚

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 本机定时器粒度（约 15 ms）使 G6 永远不可达 | `scheduleErrorP95Ms` 稳定在 10–16 ms | 走替代判据（前后 1/3 差 ≤ 2 ms 且 `|drift| ≤ 50 ms`），并把依据写进报告 `note`；CI（Linux）上优先用直接判据 |
| CI 机器性能差异导致门槛不稳 | 同代码在本地绿、CI 红（且 CPU 接近 30%） | 判定基于指标而非墙钟；CI 上打印 `host`/`compiler` 并允许按机器调整 G1 上限一次（调整必须回写 §5） |
| 机器人客户端自己成为 CPU 大户 | G1 超标但 `ac_tick_work_ms_p95` 很低 | 机器人跑在独立进程（`ac_bot`），CPU 采样只统计被测量的服务器进程 |
| 计数器口径把协议头算进带宽 | G2 在 38–41 KB/s 抖动 | 计数点固定在 `send` 的载荷参数处（不含头）；反向自检用例锁死该口径 |
| 回滚目标 | — | `git revert` 本步提交：删除 `server/tools/` 三个工具、门槛测试与 CI job，退回"只有功能测试、无性能守门"的 S13 行为 |

## 9. 移交物

**移交物 ID**：HANDOFF-S14

稳定接口：

- `ac_bot --players N --minutes M --latency MS --loss P --seed S`（无头机器人，走 UDP 传输层）。
- `ac_bench --ticks N --sheep M`：三段基准输出（stepWorld / 投影 / 差分编码）的 P50/P95 微秒。
- `ac_gate --scenario <name> --out <path> [--break ID=VALUE]`：门槛判定、报告 JSON 与退出码语义。
- 报告 JSON 字段集合与 8 条门槛 `id`（G1–G8）。
- CI job `server-perf`。

已验证能力：

- 4 人 + 60 羊 2 分钟场景在单核 < 30%、每客户端 ≤ 40 KB/s、快照 P95 ≤ 1228 B 下通过。
- 门槛自检证明判定会拦人（`--break` 退出码 1）。
- 5 分钟 soak 的 RSS 斜率 < 1 MB/分钟且房间回落；200ms RTT 场景隔墙命中为 0。
