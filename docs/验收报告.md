**硬纠正语义与可复现性（O01 定论）**：该计数来自 `/metrics` 的 `ac_hard_correct_total` 差值，
`packages/server/src/room.ts` 的 `applyPoseValidation` 在权威位移被判定不合法（速度/垂直/位置）时计数并回退。
O01 用 A/B 探针与压测把这条指标拆成了两半（证据：`docs/evidence/bots-pose-validation.json`）：

1. **派生位移被当成作弊位移（真实存在，已修）**：旧代码把权威模拟自己产生的位移（击退 / 羊群分离推挤 / 静态碰撞外推）计入命令位移预算。
   确定性探针（16 只羊贴身围困疾跑玩家 200 tick）在 `1235963` 上回退 **10 次**、修复后 **0 次**；
   该机制已由 `packages/server/src/pose-validation.test.ts` 三条用例固化。
2. **谷仓边界合法性缺陷（既有缺陷，已并入 O01 修复）**：`collideStatic` 把实体推到谷仓外墙外沿 `x = barn.minX - radius`，
   而 `isLegalPosition` 用 `> barn.minX - radius - 1e-6` 判定，仍认为该点在谷仓内 → 玩家贴墙时**每个 tick** 都被判位置非法并硬回退
   （确定性探针：200 tick → 200 次，玩家被钉死在 `x = -4.6`）。它走的是「位置非法」这条**无条件**回退路径，绕过了第 1 条的派生位移预算，
   所以只修第 1 条时数值仍为 10507 —— 该跑次 `ac_speed_violations_total` 差值为 0、`ac_pose_rejected_total` 差值 = `ac_hard_correct_total` 差值 = 10507，
   全部来自这条路径。

**修复结果**：`isLegalPosition` 的谷仓边界改为与 `collideStatic` 同语义后，同一命令的 3 次连续复跑为 **0 / 0 / 0**（`S5.2-8` 三次 `pass`），
贴墙场景由常驻用例固化为「200 tick 零回退、停在仓外沿 `x = -4.4`」。另有两点并列披露：

- 同一命令的延迟注入变体（`--latency 80 --jitter 20 --loss 0.01`）在修复前也是 0，说明 10467 这类数值**与延迟参数无关**，
  只取决于「本轮是否有机器玩家被顶在谷仓墙上」——这正好解释了 0 / 5222 / 10467 的分散。
- `--strict` 退出码仍为 1：失败项只剩 `S5.2-4` 服务端 tick 抖动 P95 ≈ 12ms（阈值 ≤8ms，本机 5ms 定时器被量化到 ~15.5ms），属 O02 范围。

**冻结契约变更记录（优化 README §7 规则 2）**：O01 执行期新增任务 11，把 `isLegalPosition` 的谷仓边界语义写进 O01 §5 冻结契约
（`x <= barn.minX - radius` 或 `x >= barn.maxX + radius` 即视为仓外，不再用 epsilon 把落点算回仓内），并同步登记到
`docs/优化/README.md` §5 门槛登记。理由：O01 §1 的目标本身就要求「静态碰撞外推」不得导致玩家位置被回退，而这条路径优先级最高、
绕过了派生位移预算；不修则 §7 DoD 的硬纠正指标无法达成（见上）。改动面 = `packages/server/src/anticheat.ts` 一行判定 + 两个用例
（`anticheat.test.ts` 边界语义、`pose-validation.test.ts` 贴墙零回退）。

### 3.6 O03 出站帧所有权与背压（本轮，2026-09-22）

原实现把 `session.outbound` / `room.broadcastBuffer` 这类**复用缓冲**直接交给 `ws`；而 `ws` 在服务端方向（不掩码）不拷贝 payload
（`node_modules/.pnpm/ws@8.21.3/node_modules/ws/lib/sender.js` 的 `if (!options.mask) return [target, data]`），
于是「写进 socket 之后又改写同一块内存」会损坏线上帧；同时慢客户端没有任何积压上限。
O03 把拷贝点收进 `packages/server/src/transport/send-queue.ts`，并给每个连接 256KiB 出站预算 + `1013` 兜底断开：

| 观测量 | 实测 | 判定 |
| --- | --- | --- |
| 复用缓冲 + 反向验证 | 把入队回调改成「计数但直传原帧」→ 新用例立刻失败：`AssertionError: expected 127 to be 24`（第 24 帧读到后来的写入） | 拷贝点承重，不能省 |
| 真实背压端到端 | 同房间聊天加压 123.3s 后：`drops 0 → 2`、`queueBytesMax = 524247`（= 2 × 262144 预算）、两个慢连接关闭码 **1013** | 有界内存 + 明确断开码 |
| 排空完整性 | 断开前积压的 **5627** 帧在恢复读取后全部解码成功，`decodeFailures = 0` | 背压下线上帧无损坏 |
| 健康连接 RSS（soak 5 分钟） | 稳态斜率 **0.278 MB/分钟**（阈值 <1）、CPU 均值 2.82% / P95 6.24%、房间回落到 0、未捕获异常 0、`verdict=pass` | `S5.2-6` pass（退出码 1 仅因 `S5.2-5` 本机未测量） |

命令、`/metrics` 采样序列与 RSS 曲线见 `docs/evidence/probe-slow-client.md`；soak 见 `docs/evidence/soak-5min-o03.{md,json}`。

**实现偏差记录（O03 §5 冻结契约的收紧）**：断开判据由 `bufferedAmount > 2 × LIMITS.maxBufferedBytes` 改为
`queue.drops > 0 && bufferedAmount >= LIMITS.maxBufferedBytes`——前者在数学上取不到（`bufferedAmount = 队列 Q + node 写缓冲`，
而写缓冲装的就是同一批未 flush 的字节，`≈ 2Q` 且 `Q ≤ maxBufferedBytes` ⇒ 上界恰为 `2 ×`）。新判据不引入新常量，语义仍是「已在丢帧且积压顶满预算」，
`docs/优化/README.md` §5 门槛登记与 O03 §5 已同步。

### 3.8 O07 武器弹药状态对账与 HUD 时效（本轮）

**结论一：本地弹药按 ack 水位对账，不再回跳。**
显示值公式 `mag = clamp(serverMag − pending, 0, magSize)`（`packages/client/src/prediction/ammoLedger.ts`），`pending` = 已本地开火但尚未被快照帧头 `lastAckedSeq` 覆盖的命令数。
这消除了「1Hz 权威值无条件覆写本地预测」造成的回跳——原先冲锋枪 1 秒内可打 8 发，下一帧 `matchState` 到达时弹药数会突然变多。
对账水位复用既有字段（**未改协议**），`noteServerAck` 只在 seq 严格增大时推进，回退忽略、`reset()` 与 `reconciler.reset()` 同点调用。

| 情形 | 断言（`packages/client/src/prediction/ammoLedger.test.ts`） |
|---|---|
| 本地打 3 发、ack 未追上 | `mag = 30 − 3 = 27`、`pending = 3`、`rejected = 0`（**核心：不回跳**），同一帧重复 `reconcile` 不重复结算 |
| ack 追上且权威同步下降 | `pending = 0`、`rejected = 0`、`mag = 27` |
| ack 追上但权威只降 1 | `rejected = 2`、`overridden = true`、`mag = 权威值 29`（被拒的本地开火不再静默丢失） |
| 换弹完成（权威上升） | `pending` 清空、`mag = 30`、`reserve = 120` |
| 环形缓冲溢出 | 计数 > 0、`overridden = true`、`mag = 权威值`（不出现负弹药） |

**结论二：HUD 换弹/狂暴倒计时本地推进 + 权威重同步。**
`packages/client/src/combat/localTimers.ts`：每帧按 `dtMs` 递减，权威值到达时取 `min(本地, 权威 + 单帧容差 SERVER_TICK_MS)`，本地已归零时采用新一轮权威值；下限 0、迟到帧不会让剩余变大。
`main.ts` 每帧调用 `advance(dtMs)` 并把结果写入 `combatState.reloadLeftMs / rageLeftMs`（换弹环与狂暴文本因此连续变化，不再 1Hz 阶梯）。
证据：`localTimers.test.ts` 五组用例（16ms × 60 → 剩余减少 960ms；权威更紧急立即采用；迟到帧不变大；下限 0 且归零后可重启新一轮；狂暴/换弹互不干扰）。

**人工观察步骤（目标机，本机无浏览器未执行）**：`pnpm dev` → 浏览器开两窗口进同一房间 → 按住开火 10 秒，观察弹药数字
（应只随实际消耗下降、不再"打空后突然回弹"）；按 R 换弹观察换弹环连续转动；拾取狂暴道具后观察倒计时文本逐帧递减。
调试面板（`?debug=1` + F3）新增一行 `ammo pending … rejected … div … resync …` 可直接读出对账状态。

### 3.10 O09 战绩存储与 HTTP 层（本轮）

原缺口：战绩文件整块读入内存且常驻数组无上限；排行榜/最近对局每次请求全量排序（并重复计算同一条记录）；HTTP 读接口既无限流也无缓存；`reports/` 没有保留策略。

| 缺口 | 修复 | 证据 |
|---|---|---|
| 整文件读入 + 无上限 | `createReadStream` + `readline` 流式加载；`DEFAULT_MAX_RECORDS = 10000` 超出按 `startedAtMs` 最旧批量淘汰（文件不截断） | 10 万行 665 B/行：`heapUsed` 增量 **132.2 MB → 6.9 MB**，常驻 **100 000 → 10 000** 条（`docs/evidence/store-load-100k.md`） |
| 每次全量排序 | `topCache` / `recentCache`，`invalidateCaches()` 单点失效（load / append / 淘汰） | `listTopScores(20)` 49.46 ms → 0.001 ms（稳态）；与「全排序取前 N」逐条对拍一致（含并列决胜） |
| 读接口无限流/缓存 | 30 次/分钟/IP（`429` + `retry-after: 60`）+ 60s TTL 缓存（键 `path:limit`，`store.version` 变化即失效） | `packages/server/src/http.test.ts`（429 / 缓存命中 / 写入后失效）+ `docs/evidence/http-limit-o09.md` |
| `reports/` 无保留策略 | `retainReports(dir, keep)` 按 mtime 保留最近 `REPORT_RETENTION`（默认 200，`0` = 不清理），失败不抛 | `packages/server/src/report.test.ts`（保留 N / 目录不存在 / 删除失败不抛） |
| 指标不可见 | 新增 `ac_records_retained`（gauge）、`ac_http_rate_limited_total`、`ac_http_cache_hits_total`（counter） | `/metrics` 输出 + `http.test.ts` 断言 |

**如实披露**：10 万行加载耗时从 445 ms 变为 711 ms（×1.6，流式逐行 + 淘汰的代价），换来内存 1/19 且不随文件增长——两个数字都写进本报告与证据文件，未只报优势。
