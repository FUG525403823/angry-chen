# 文档地图

本目录是《愤怒的陈sir vs 发疯的羊群》**v2（C++ 权威服务器 + Unity 客户端）**的全部施工依据。按顺序读、按顺序做，不需要额外的口头上下文。

## 0. 仓库长什么样

| 目录 | 内容 |
|---|---|
| `server/` | C++20 权威服务器（S01–S15 链的落点） |
| `client/` | 团结引擎（Tuanjie，Unity 2022.3 线）+ URP 客户端（C01–C15 链的落点） |

| `docs/` | 本目录：共识、需求、选型与两条线性计划链 |

- v1 的 TypeScript 全栈实现（`packages/**`）、Node/pnpm 工具链、Docker 与反代配置、以及只描述 v1 的文档（`P01–P10`、`O01–O10`、`evidence/`、验收报告、运维手册、部署清单）已随重构**移出仓库**；冻结副本在 `D:\projects\tmp\angry-chen-bak`（含 `node_modules`，可直接跑 v1 做基准对照）。
- 两份计划链里出现的 `packages/**` 路径，一律指**上述备份仓库**里的冻结实现。
- v2 的 `docs/evidence/` 是本轮**新建**的证据目录（对拍向量 `fixtures/`、验收与审计报告），与上一条已移出的 v1 `evidence/` 无关。
- 本仓库的门禁是 `node tools/check-docs.mjs && node tools/check-assets.mjs`，两步都必须退出码 0。

## 3. 施工：两条各自线性的计划链

索引、里程碑、跨链前置与**推荐交错执行顺序**见 [plans-v2/README.md](plans-v2/README.md)（该顺序由 `order` 注释机器校验）。

| 链 | 文档 | 里程碑 |
|---|---|---|
| 服务器 | [plans-v2/server/S01-C++工程基线与构建质量门.md](plans-v2/server/S01-C++工程基线与构建质量门.md) → S15 | MS01–MS15 |
| 客户端 | [plans-v2/client/C01-Unity工程基线与构建.md](plans-v2/client/C01-Unity工程基线与构建.md) → C15 | MC01–MC15 |

两条链**各自线性**：链内的第 N 份的入口条件等于第 N−1 份的移交物；跨链只允许引用顺序表中排在更早的计划。

## 4. 线性保证机制

1. **入口/出口成对**：每份计划 §2「入口条件」列出必须已成立的事实（附验证命令），§9「移交物」列出交给下一步的稳定接口与已验证能力。第 N 份的 §9 ID 必须等于第 N+1 份的 §2 ID。
2. **只允许引用已冻结的契约**：链内不得引用编号大于自身的计划；跨链引用必须是顺序表中更早的计划（`node tools/check-docs.mjs` 会逐条检查）。
3. **一次会话一份**：每份计划的 §4 任务清单 5–9 项，能在一次会话内做完；任务过大就拆成新的编号，不挤在一份里。
4. **冻结契约不留活口**：字段、常量、阈值一律写死，禁止 `TBD`/`待定` 进入 §5。

## 5. 门禁

| 命令 | 检查 | 失败意味着 |
|---|---|---|
| `node tools/check-docs.mjs` | 必需文档齐备、双链编号连续、九段式齐全、§2/§9 移交物守恒、`order` 前向依赖、docs 内相对链接可达 | 文档链或链接被破坏 |
| `node tools/check-assets.mjs` | 零外部素材（扩展名黑名单 + 二进制嗅探）、依赖白名单（`client/Packages/manifest.json`、`server/CMakeLists.txt`） | 引入了素材或第三方依赖 |
| 链内门 | S01 的 CMake + `ac_tests`、C01 的编辑器批处理自检（`-executeMethod`，见各计划 §6） | 该阶段的构建/测试未达标 |

改完文档或加入新文件后，两条 Node 门禁必须都退出码 0 再提交。

## 6. 写文档的纪律

- 变更冻结契约（协议字段、量化规则、数值表 schema、公开函数签名）时：先改对应 ADR，再改代码，最后同步受影响文档。
- 一份计划只描述一件事；跨越多个里程碑的改动必须拆成多份计划。
- v1 的决策与文档不删改历史结论，只在 ADR 里标注取代关系；v2 的决策进 ADR-008/009/010 及其后继。
