# 技术选型

> 本文是十份计划文档（P01–P10）的**技术前提**。文中每条"实测"都附可复现命令；未实测的判断一律标注为"判断"。

## 1. 选型约束（决定性的四条）

| 约束 | 事实依据 | 对选型的影响 |
|---|---|---|
| 单人开发、要能被文档线性驱动 | 项目要求"十份文档顺序执行即可完成" | 技术栈必须让每个阶段的产物可独立运行、可自动化验证；拒绝需要 GUI 编辑器才能施工的引擎 |
| 开发机环境固定且受限 | 实测：Node 24.14.1 / pnpm 11.22.0 / win32 x64 / 16 核；`docker`、`go`、`rustc` 均不存在 | 只用 Node 生态；发布链不依赖容器；不引入需要原生编译的包 |
| 零外部素材 | 项目要求：羊额有「问界」标志，且仓库不得依赖下载资源 | 渲染与音频必须能纯代码生成；拒绝需要素材包的框架 |
| 需要联机与手感 | 玩法是 1–4 人协作射击 PVE | 必须有权威服务器与客户端预测的能力，且这份能力要能被测试（不靠人眼看画面） |

## 2. 选型结论一览

| 层次 | 选择 | 锁定版本 | 一句话理由 |
|---|---|---|---|
| 语言 | TypeScript | 5.9.3 | 端到端同一套类型，协议字段与世界结构在两侧共享；5.9.3 是 lint 生态允许的最高线 |
| 仓库 | pnpm workspace（`@ac/shared` / `@ac/server` / `@ac/client`） | pnpm 11.22.0 | 单一 `shared` 源码同时被服务器、客户端、无头机器人消费 |
| 运行时 | Node.js | 24.14.1 | 环境既有；原生 ESM、`worker_threads`、内置 `fetch` |
| 服务端执行 | tsx | 4.23.13 | 实测 Node 原生类型剥离对 workspace 软链失败，tsx 通过；换来服务端零构建产物 |
| 客户端构建 | Vite | 8.3.0 | 原生 ESM 开发服务器、极快 HMR、与 vitest 同源 |
| 渲染 | three.js | 0.186.0 | WebGL2 成熟、几何体/材质/实例化齐全，足以用纯代码生成全部美术 |
| 网络 | `ws` + 手写二进制协议 | 8.21.3 | 浏览器唯一无信令可用的双向通道；协议手写以完全掌控量化与差分 |
| 测试 | vitest + @vitest/coverage-v8 | 5.0.1 | 与 Vite 同配置；可在无浏览器环境下测 `shared` 与 `server` 集成 |
| 静态检查 | eslint（flat config）+ typescript-eslint + prettier | 10.11.0 / 8.70.0 / 3.9.8 | 类型感知 lint 是质量门的一部分 |
| UI | 原生 DOM + CSS 变量 | — | HUD/大厅是少量控件，不值一个框架依赖 |
| 数学 | 自研最小 `Vec3`（`shared/src/math.ts`） | — | `shared` 不得依赖 three；服务端不需要矩阵栈 |
| 持久化 | `MatchStore` 接口 + NDJSON 适配器 | — | MVP 数据量极小；缝已留好给将来的 sqlite 适配器 |
| 部署 | 单 Node 进程 + Caddy/Nginx 反代 WSS | — | 本机无 docker，不能让发布链依赖它 |

## 3. 分层论证

### 3.1 为什么是"一份模拟，三处消费"

联机射击的核心难点是"服务器权威"与"客户端手感"之间的张力：客户端必须立刻响应，服务器必须最终说了算。当两端**调用同一个 `stepWorld`** 时，这个张力才可控——预测与权威的差异只剩网络时延，而不是两套逻辑的实现分歧。

因此 `@ac/shared` 被规定为**纯净模块**（禁 three / DOM / `node:*` / `Math.random` / `Date.now`），并暴露三个函数作为唯一接口：

```ts
createWorld(seed: number, cfg: WorldConfig): World
stepWorld(world: World, commands: readonly Command[], dtMs: number): void
snapshotWorld(world: World, out: SnapshotBuffer): void
```

这三处消费方是：服务器权威步进、客户端预测步进、`tools/bots.mjs` 无头压测机器人。接口小、行为深，测试也在同一个缝上进行。

### 3.2 为什么服务端零构建产物（以及代价）

实测结论（三条，都是选型的硬依据）：

1. `node <file>.ts` 在本机可运行（strip-only 模式默认开启）。
2. 但当 `.ts` 文件经由 `node_modules` 解析（pnpm workspace 软链即如此）时，抛 `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`；`--preserve-symlinks` 也无法绕过。
3. `tsx@4.23.13` 在同一场景下正常执行。

所以：要么给 `shared` 加构建步骤（`tsc` 产出 dist + `exports` 条件导出），要么引入 `tsx`。选择后者——`tsx` 只做类型剥离，不引入额外的模块语义，且省掉"改了 shared 忘记重新构建"这类伤病。

配套约束：`erasableSyntaxOnly` 编译项保证语法始终可剥离（实测 `enum` 与构造器参数属性会抛 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`），于是"将来去掉 tsx"这条路一直是开着的。

### 3.3 为什么 TypeScript 不用最新的 7.0.2

实测 `typescript-eslint@8.70.0` 的 peer 范围是 `>=4.8.4 <6.1.0`。质量门依赖类型感知 lint（尤其是 `shared` 的纯净性规则），因此锁 `typescript@5.9.3`。复查触发条件：`typescript-eslint` 放开上限且本仓库 `pnpm check` 全绿。

### 3.4 为什么客户端直连 `shared` 源码

`@ac/shared` 的 `exports` 指向 `./src/index.ts`。Vite 与 vitest 都能解析，改 shared 立即触发 HMR；代价是需要在相对导入里写 `.ts` 扩展名（已写入工程约定），以及可能需要 `optimizeDeps.exclude: ['@ac/shared']`（P01 的已知风险项）。

### 3.5 为什么 WebSocket 而不是 UDP 语义的通道

浏览器不能发裸 UDP。可选的"不可靠"通道只有 WebRTC DataChannel（需要信令与 STUN/TURN，且 Node 端服务端实现不够成熟）与 WebTransport（Node 侧尚无成熟服务端实现）。因此：

- 传输用 WebSocket/TCP，并用手法把 TCP 的队头阻塞代价压到可接受：快照小（≤2KB）、**不重传**、晚到的旧快照直接丢弃（按 tick 单调性）、命令只发最新、客户端 100ms 插值缓冲。
- 协议编解码与 `Transport` 缝分离，未来切 WebTransport 只换适配器，不动 `sim` 与字段。
- 完整取舍见 [ADR-002](00-共识/ADR/ADR-002-网络模型与协议.md)。

### 3.6 为什么全部美术程序化生成

需求要求羊额头带「问界」标志，而仓库必须零外部素材。three.js 的基础几何体 + `InstancedMesh` + `CanvasTexture` + WebAudio 合成足以覆盖：羊形、武器视模型、额标、枪口火焰、曳光、弹孔、毛屑、UI 图标与音效。策略与合规判定见 [ADR-003](00-共识/ADR/ADR-003-美术素材与问界标识策略.md)。

### 3.7 为什么不用 React

HUD 与大厅合计约十来个控件，没有复杂表单、没有 SSR、没有路由。原生 DOM + CSS 变量 + 少量手写绑定即可，且能让 UI 更新与 60FPS 渲染循环解耦（避免框架重渲染模式与逐帧状态混合）。判断：省下的依赖与心智负担大于收益。

## 4. 候选方案对比矩阵

| 维度（权重） | A：TS 全栈单仓 | B：Unity/Godot | C：Phaser 2D + Colyseus | D：Rust/C++ 服务端 |
|---|---|---|---|---|
| 与"文档线性驱动"的契合（高） | 强：每阶段产物是文本 + 可跑命令 | 弱：需引擎编辑器与场景文件 | 中：逻辑可控但框架遮蔽协议 | 弱：需先解决工具链 |
| 本机可验证性（高） | 强：vitest 无头全覆盖 | 弱：需构建与引擎运行 | 中 | 弱 |
| 联机手感能力（高） | 强：自控预测/和解/回滚 | 中：依赖引擎 Netcode | 中：状态同步框架受限 | 强但项目用不上 |
| 零外部素材（高） | 强：全程序化 | 弱：引擎资产流程 | 中 | 强 |
| 环境可行性（高） | 强：Node 已就位 | 弱：无引擎工具链 | 强 | 弱：无 rustc/go |
| 上手/维护成本（中） | 强：单一语言 | 中 | 中 | 弱 |

结论：**A 在五个高权重维度上全面胜出**，且是唯一能同时满足"零外部素材"与"无 GUI 施工"的方案。

## 6. 风险与替代路径

| 风险 | 触发信号 | 替代路径 |
|---|---|---|
| TCP 队头阻塞影响手感 | 实测丢包 >3% 且可感知卡顿 | 换 `Transport` 适配器为 WebTransport/WebRTC，协议字段不变 |
| `tsx` 带来的额外启动开销 | 冷启动 >1s 或 watch 频繁重启变慢 | 给 `shared`/`server` 加 `tsc` 构建产物，`exports` 增加 `default` 条件 |
| Vite 预打包 workspace `.ts` 依赖出问题 | 开发服务器报依赖优化错误 | `optimizeDeps.exclude: ['@ac/shared']`，并在 P01 写死 |
| three.js 大版本升级破坏 API | 升级后类型报错 | 精确锁定 0.186.0，升级需单独 ADR |
| 程序化美术观感不足 | 内部观感清单不通过 | 把预算投到可读性（轮廓光/雾/特效），而非外部素材 |
| 规模增长超出单进程 | 房间数 > MAX_ROOMS 或 CPU 饱和 | 房间维度分片：多进程 + 房间路由；`MatchStore` 换集中式适配器 |
